# Работа с Laterna VTT

Self-hosted VTT: FastAPI, React/TypeScript, PixiJS 8, один Zustand-store.
Исторический baseline завершения FSD-09b (PR #25):
`ff9681769978e295a763bcdea8aba536b7967566`. Перед каждой новой задачей проверять
актуальный master, рабочую ветку, HEAD соответствующего PR и локальный diff.
Исторический SHA — для изучения решений и сравнения, не для автоматического
возврата к старому состоянию. Исторические результаты CI не выдавать за проверки
новых изменений. Перед работой читать [архитектуру](docs/ARCHITECTURE.md),
[Beta-решения](docs/BETA_DECISIONS.md), [roadmap](docs/ROADMAP.md) и
[руководство по разработке и проверкам](docs/DEVELOPMENT.md). Не перезаписывать чужие изменения.

- Frontend: app композиция → pages/widgets/features → entities/shared;
  systems/dnd5e предоставляет projections/UI slots, static bindings находятся в app.
  Один плоский store, Session/Campaign/Gameplay/UI; UI использует state/public,
  app/session — ограниченный state/bridge. Entities/shared/systems не импортируют store.
- Backend пока в server/app с основными main.py/handlers.py и доменными helpers.
  Практичный модульный монолит, DataHome и Alembic — утверждённая цель, не реализация.
- Порядок Beta: **A** LOS/базовый свет/FoW → **B** сохранность, DataHome, backup/restore,
  Alembic и постепенный backend → **C** кампании/AccessPolicy → **D** остальные
  обязательные функции Beta C → **E** стабилизация. Если PB-01 или другая задача A
  требует новой схемы или несовместимых persisted data, сначала необходимая часть
  DataHome/backup/Alembic
  и безопасного upgrade из B.
- Сервер авторитетен для команд, прав, бросков и проверки секретности/видимости.
  Не выдавать неавторизованным игрокам скрытые объекты, данные ГМ и приватные медиа.
  Сохранять API, seq/cmd_id/base_seq, reconnect и совместимость сохранений.
- PB-01 — чистая геометрия LOS, расчёт видимости, базовая модель света и тесты.
  PB-02 — серверная проверка разрешённой видимости, фильтрация защищённых объектов
  и получателей, предотвращение утечек через REST/WS/media. Геометрическое ядро
  пригодно для серверной логики, но само не является механизмом авторизации.
  Не объединять PB-01/PB-02 без отдельного архитектурного решения.
- Перед реализацией LOS изучить LATERNA_SCENE_CORE_AUDIT.md, если доступен локально
  или в материалах проекта. Его исторические рекомендации не становятся APPROVED
  автоматически; при отсутствии файла сообщить об этом, не придумывать содержание.
- PixiJS — renderer, не граница безопасности; высокочастотные координаты и
  drag-preview не переносить в Zustand.
  Beta rules engine — D&D 5e 2014; ключи dnd5e/mob сохраняются, SDK не вводится.
- Не менять пользовательские БД/сохранения без явного разрешения. Не выполнять reset,
  reset/clean Git, удаление uploads/ключей/DataHome или down -v для игровых данных.
  Перед разрешённой миграцией — проверяемый backup/restore; исходник Alpha сохранять.
  Тесты используют только изолированные временные DB/uploads/ключи.
- Для затронутых частей — профильные проверки; перед готовым PR — необходимые
  backend/frontend/typecheck/build/Chromium по AGENTS и CI_CD. Не ослаблять assertions,
  counts или gate. Fast CI точного commit SHA — между этапами; Full CI актуального
  test merge + CI required — для ready PR. Fast CI не разрешает merge.
- Актуальный Git-регламент — ниже; он заменяет прежнее требование отдельного
  разрешения для каждого commit/push/Draft PR в старых инструкциях. Более узкие
  ограничения текущего задания имеют приоритет. Не начинать следующий PB автоматически.
- Все сообщения Git-коммитов — на русском; Conventional Commits допустимы,
  описание после двоеточия — русское. Не публиковать секреты, логи и игровые данные.

## Git workflow

- Каждый PB выполнять в отдельной рабочей ветке от проверенного актуального master.
  После необходимых успешных локальных проверок самостоятельно выполнять логические
  коммиты, обычный push рабочей ветки и создавать Draft PR. Повторное разрешение
  на эти действия не требуется. Код должен быть доступен для независимого review.
- Замечания исправлять в той же ветке и том же PR; не создавать новый PR для
  исправления замечаний к открытому. Один PR — один связанный блок изменений.
- Независимое архитектурное review должно быть явно привязано к номеру PR и
  конкретному полному HEAD SHA. Собственная проверка агента не является независимым
  одобрением. При изменении HEAD сравнить diff с одобренным SHA; содержательные
  изменения кода или инструкций требуют повторного review изменённой части.
- После положительного независимого архитектурного review разрешено самостоятельно
  пройти Ready → Full CI → обычный Merge commit с сохранением истории. Перед merge
  повторно сверять head/base/test merge SHA, отсутствие конфликтов и успешный
  CI required для актуального test merge. Fast CI не заменяет Full CI.
- Не объединять PR с нерешёнными блокерами безопасности, совместимости данных
  или архитектуры. Не обходить branch protection, не делать force-push, прямой
  push в master и не ослаблять tests/counts/timeouts/gate.
- После merge проверить Full CI именно нового master. Только после success удалить
  собственную remote-ветку, если она больше не используется и не содержит лишних
  коммитов. Локальные ветки с незакоммиченными изменениями не удалять.
- Другие ветки без PR удалять автоматически лишь при доказанном отсутствии
  уникальных коммитов и незакоммиченных изменений; неоднозначные ветки сохранить
  и перечислить в отчёте. Проверять другие открытые PR и зависимости веток.
- Публикация релиза, изменение защиты master и работа с пользовательскими данными
  требуют отдельного явного разрешения. Автоматическое продолжение следующего PB
  этим регламентом не разрешено.
- Ограничения остановки относятся к конкретному заданию. Для текущего review PB-00
  исправления публикуются в Draft, затем требуется повторное review нового HEAD
  до Ready/merge. Это правило этой задачи, не вечное исключение для будущих PB;
  следующие PB выполнять по актуальному регламенту и ограничениям их задания.

Исторические FSD-аудиты/концепции сохраняют свои базы и измерения. APPROVED в
[реестре Beta](docs/BETA_DECISIONS.md) не означает AS-IS; детали OPEN не выбирать
молчаливо. Запрет реализации LOS, backend-рефакторинга и миграций относится только
к документационной задаче DOCS-00. Последующие задачи могут выполнять эти работы
по отдельному разрешению владельца, после проверки актуальных архитектурных
контрактов и обязательных migration gates.
