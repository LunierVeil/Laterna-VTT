# Рабочий процесс Laterna VTT с Codex

Обязательные правила проекта собраны в [AGENTS.md](../../AGENTS.md). Навыки ниже
можно явно вызвать через `$имя-навыка` в Codex. Они доступны из корня и вложенных
каталогов рабочей копии. [Документация Codex Skills](https://learn.chatgpt.com/docs/build-skills).

## Начало задачи

Запустите Codex в нужной рабочей копии и используйте
[`$task-start`](../../.agents/skills/task-start/SKILL.md). Сверьте задание с актуальными
master, веткой, локальным diff и PR. Для действующего PR продолжайте работу в его
ветке. Сохраните в чате основание ветки, границы задачи, критерии и точку остановки.

При первом проходе найдите точки входа и тесты, затем читайте только относящиеся
к ним разделы документов из AGENTS.md. Учитывайте локальные инструкции по
затронутым каталогам даже при запуске из корня. В заметках сохраняйте пути,
символы и ссылки на решения, а также SHA, на котором они проверены. При
продолжении обновляйте сведения по изменившимся файлам и контрактам. Исторические
срезы используйте для сравнения. Текущее поведение подтверждайте кодом.

## Спецификация и план

Для задачи или Issue с изменением контрактов вызовите
[`$spec-first`](../../.agents/skills/spec-first/SKILL.md).
В [шаблоне задачи](TASK_TEMPLATE.md) сформулируйте наблюдаемый результат, границы,
критерии приёмки и проверку для каждого критерия. Укажите затронутые контракты
и решения владельца. При изменении поведения опишите ошибки и совместимость
там, где они влияют на приёмку. Открытое решение, от которого зависит
реализация, вынесите на согласование до этой реализации.

Для небольшой однозначной правки достаточно критериев в задании и прямой
реализации. Спланируйте работу при изменении нескольких контрактов, протокола,
прав или сохранений. Укажите порядок правок, зависимости и проверки на
границах этапов. Интерактивный `/plan` в Codex CLI подходит для отдельного
планирования. [Команды Codex CLI](https://learn.chatgpt.com/docs/developer-commands?surface=cli).

## Выбор навыков по задаче

Полный маршрут проходит от `$task-start` через `$spec-first`, `$tdd`, `$qa`,
`$pr-preflight` и `$ci` до `$handoff-create` при паузе. Выбирайте нужные шаги.
Передавайте следующему шагу критерии и результаты предыдущего.

| Задача | Маршрут |
| --- | --- |
| Опечатка | `$task-start` → профильная проверка → `$pr-preflight`. |
| Frontend-регрессия | `$task-start` → [`$tdd`](../../.agents/skills/tdd/SKILL.md) → [`$qa`](../../.agents/skills/qa/SKILL.md) → `$pr-preflight`. |
| Изменение архитектурного контракта | `$task-start` → `$spec-first` → согласование открытых решений → `$tdd` → `$qa`. |
| Разбор упавшего запуска Actions | [`$ci`](../../.agents/skills/ci/SKILL.md) по URL run или номеру PR. |

[Проверки Workflow-02](WORKFLOW_02_VALIDATION.md) показывают применение навыков
на действующих контрактах и исторических запусках.

## Пауза и продолжение

Перед паузой используйте [`$handoff-create`](../../.agents/skills/handoff-create/SKILL.md).
Если история доступна, запустите `codex resume` из той же рабочей копии и
выберите нужную сессию. В сохранённой или новой сессии вызовите
[`$handoff-resume`](../../.agents/skills/handoff-resume/SKILL.md) с путём записи.
После исчерпания лимита используйте последний доступный handoff. При его отсутствии
восстановите состояние по задаче, Git и PR, начиная с ближайшего незавершённого шага.

### Запись handoff

Краткий Markdown-файл в корневом `.agent-handoffs/` содержит:

- Задачу, ссылку на спецификацию при наличии, ограничения и точку остановки.
- Ветку, полный локальный HEAD, PR и его полный HEAD при наличии, статус Git и пути локальных правок.
- Завершённое, ссылки на существенные решения и затронутые точки входа.
- Выполненные проверки с привязкой к SHA или рабочему дереву. Отдельно оставшиеся проверки и блокеры.
- Ближайший разрешённый шаг и известное состояние внешних действий.

## Draft PR и доказательства проверок

Перед публикацией используйте [`$pr-preflight`](../../.agents/skills/pr-preflight/SKILL.md).
Проверьте весь diff, профильные команды из [DEVELOPMENT](../DEVELOPMENT.md#все-проверки)
и ограничения задания. В описании PR свяжите изменение с критериями и
перечислите проверки с результатом. Для локальной проверки укажите команду,
итог, количество тестов при наличии и проверенный SHA или состояние рабочего
дерева. Для CI укажите workflow, ссылку, событие, SHA и итог. Используйте статусы
«прошла», «упала», «выполняется», «запланирована» или «пропущена» с причиной.

После push сверяйте полный HEAD в Draft с SHA коммита. Для Fast CI проверяйте
успешный запуск на событии `push` рабочей ветки, где `headSha` равен полному
HEAD и оба jobs, backend и frontend, завершились успешно. Запуск на
`pull_request` проверяет GitHub test merge. Для Ready и merge применяются
условия [Git workflow](../../AGENTS.md#git-workflow) и [CI/CD](../CI_CD.md).
`$ci` собирает доказательства для конкретных run, attempt и SHA.

## Независимое review и делегирование

Передайте отдельному ревьюеру задачу и критерии, номер PR, полный HEAD,
diff и результаты проверок. Попросите проверить соответствие scope,
архитектурные границы, серверную авторизацию, совместимость и тесты в
затронутых частях. Решение должно явно называть PR и полный HEAD. Замечание
должно указывать файл или контракт, последствие и условие его проявления.
Перепроверка после смены HEAD регулируется [Git workflow](../../AGENTS.md#git-workflow).

Встроенный `/review` помогает провести самопроверку. Subagents допустимы при
разрешённой в задании или действующих инструкциях делегации, когда область
работы можно изолировать и результат проверяем. Для поиска и ревью задайте
read-only scope, необходимые источники и ожидаемый результат. Для параллельных
правок нужны непересекающиеся области записи. Основной агент отвечает за
интеграцию и проверки. Вывод subagent сам по себе не закрывает обязательное
независимое архитектурное review. [Subagents в Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents).
