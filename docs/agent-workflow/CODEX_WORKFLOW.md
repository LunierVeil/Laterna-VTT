# Рабочий процесс Laterna VTT с Codex

Обязательные правила проекта собраны в [AGENTS.md](../../AGENTS.md). Навыки ниже
можно явно вызвать через `$имя-навыка` в Codex. Они доступны из корня и вложенных
каталогов рабочей копии. [Документация Codex Skills](https://learn.chatgpt.com/docs/build-skills).

## Начало задачи

Запустите Codex в нужной рабочей копии и используйте
[`$task-start`](../../.agents/skills/task-start/SKILL.md). Сверьте задание с актуальными
master, веткой, локальным diff и PR. Для действующего PR продолжайте работу в его
ветке. Сохраните в чате основание ветки, границы задачи, критерии и точку остановки.

При первом проходе найдите точки входа и тесты, затем читайте только относящиеся
к ним разделы документов из AGENTS.md. Учитывайте локальные инструкции по
затронутым каталогам даже при запуске из корня. В заметках сохраняйте пути,
символы и ссылки на решения, а также SHA, на котором они проверены. При
продолжении обновляйте сведения по изменившимся файлам и контрактам. Исторические
срезы используйте для сравнения. Текущее поведение подтверждайте кодом.

## Спецификация и план

Для задачи или Issue с изменением контрактов вызовите
[`$spec-first`](../../.agents/skills/spec-first/SKILL.md).
В [шаблоне задачи](TASK_TEMPLATE.md) сформулируйте наблюдаемый результат, границы,
критерии приёмки и проверку для каждого критерия. Укажите затронутые контракты
и решения владельца. При изменении поведения опишите ошибки и совместимость
там, где они влияют на приёмку. Открытое решение, от которого зависит
реализация, вынесите на согласование до этой реализации.

Для небольшой однозначной правки достаточно критериев в задании и прямой
реализации. Спланируйте работу при изменении нескольких контрактов, протокола,
прав или сохранений. Укажите порядок правок, зависимости и проверки на
границах этапов. Интерактивный `/plan` в Codex CLI подходит для отдельного
планирования. [Команды Codex CLI](https://learn.chatgpt.com/docs/developer-commands?surface=cli).

## Выбор навыков по задаче

Полный маршрут проходит от `$task-start` через `$spec-first`, `$tdd`, `$qa`,
`$pr-preflight` и `$ci` до `$handoff-create` при паузе. Выбирайте нужные шаги.
Передавайте следующему шагу критерии и результаты предыдущего.

| Задача | Маршрут |
| --- | --- |
| Опечатка | `$task-start` → профильная проверка → `$pr-preflight`. |
| Frontend-регрессия | `$task-start` → [`$tdd`](../../.agents/skills/tdd/SKILL.md) → [`$qa`](../../.agents/skills/qa/SKILL.md) → `$pr-preflight`. |
| Изменение архитектурного контракта | `$task-start` → `$spec-first` → согласование открытых решений → `$tdd` → `$qa`. |
| Разбор упавшего запуска Actions | [`$ci`](../../.agents/skills/ci/SKILL.md) по URL run или номеру PR. |

[Проверки Workflow-02](WORKFLOW_02_VALIDATION.md) показывают применение навыков
на действующих контрактах и исторических запусках.

## Пауза и продолжение

Перед паузой используйте [`$handoff-create`](../../.agents/skills/handoff-create/SKILL.md).
Если история доступна, запустите `codex resume` из той же рабочей копии и
выберите нужную сессию. В сохранённой или новой сессии вызовите
[`$handoff-resume`](../../.agents/skills/handoff-resume/SKILL.md) с путём записи.
После исчерпания лимита используйте последний доступный handoff. При его отсутствии
восстановите состояние по задаче, Git и PR, начиная с ближайшего незавершённого шага.

### Запись handoff

Краткий Markdown-файл в корневом `.agent-handoffs/` содержит:

- Задачу, ссылку на спецификацию при наличии, ограничения и точку остановки.
- Ветку, полный локальный HEAD, PR и его полный HEAD при наличии, статус Git и пути локальных правок.
- Завершённое, ссылки на существенные решения и затронутые точки входа.
- Выполненные проверки с привязкой к SHA или рабочему дереву. Отдельно оставшиеся проверки и блокеры.
- Ближайший разрешённый шаг и известное состояние внешних действий.

## Draft PR и доказательства проверок

Перед публикацией используйте [`$pr-preflight`](../../.agents/skills/pr-preflight/SKILL.md).
Проверьте весь diff, профильные команды из [DEVELOPMENT](../DEVELOPMENT.md#все-проверки)
и ограничения задания. В описании PR свяжите изменение с критериями и
перечислите проверки с результатом. Для локальной проверки укажите команду,
итог, количество тестов при наличии и проверенный SHA или состояние рабочего
дерева. Для CI укажите workflow, ссылку, событие, SHA и итог. Используйте статусы
«прошла», «упала», «выполняется», «запланирована» или «пропущена» с причиной.

После push сверяйте полный HEAD в Draft с SHA коммита. Для Fast CI проверяйте
успешный запуск на событии `push` рабочей ветки, где `headSha` равен полному
HEAD и оба jobs, backend и frontend, завершились успешно. Запуск на
`pull_request` проверяет GitHub test merge. Для Ready и merge применяются
условия [Git workflow](../../AGENTS.md#git-workflow) и [CI/CD](../CI_CD.md).
`$ci` собирает доказательства для конкретных run, attempt и SHA.

## Независимое review и делегирование

Передайте отдельному ревьюеру задачу и критерии, номер PR, полный HEAD,
diff и результаты проверок. Попросите проверить соответствие scope,
архитектурные границы, серверную авторизацию, совместимость и тесты в
затронутых частях. Решение должно явно называть PR и полный HEAD. Замечание
должно указывать файл или контракт, последствие и условие его проявления.
Перепроверка после смены HEAD регулируется [Git workflow](../../AGENTS.md#git-workflow).

Встроенный `/review` помогает провести самопроверку. Вывод внутреннего
subagent не закрывает обязательное независимое архитектурное review.

## Multi-Agent Review

Используйте делегирование, если оно разрешено заданием или действующими
инструкциями и проверку можно ограничить несколькими контрактами.

| Область | Кого вызвать |
| --- | --- |
| Небольшая правка | Самопроверка или одна роль, если нужен профильный разбор. |
| Backend | `backend_review`. При изменении архитектурной границы добавьте `architecture`. |
| Frontend | `frontend_review`. При изменении архитектурной границы добавьте `architecture`. |
| Контракт между frontend и backend | `architecture`, `backend_review` и `frontend_review` очередями. |
| Доказательства CI или диагностика Actions | `ci_review` с номерами PR, run и attempt. |

1. Выполните `$task-start` и зафиксируйте репозиторий, PR, HEAD/base и состояние
   рабочего дерева. Передайте точный diff, критерии из `$spec-first` при наличии,
   затронутые контракты и ожидаемую проверку. Для CI используйте `$ci` или передайте
   роли полученные им свидетельства. Передавайте выбранные результаты `$tdd` и `$qa`
   с отметкой о проверенном состоянии.
2. В сессии Codex попросите явно по имени. Например: «Запусти один subagent
   `backend_review` по PB-07 C на указанном HEAD, дождись отчёта и верни его».
   CLI обнаруживает проектные роли по полю `name` в `.codex/agents/`.
   Проверьте доверие к проекту перед загрузкой его настроек. В интерактивном CLI можно открыть поток через `/agents`. При пакетном
   запуске `codex exec --json` проверяйте фактический запуск и отчёт дочерней
   сессии. В CLI 0.171.0 для этого используйте сессию со служебной историей.
3. Держите не больше двух открытых дочерних потоков. Дождитесь отчётов и
   закройте завершённые потоки перед следующей группой. Роли не делегируют
   дальше. Проектный лимит задаёт `agents.max_concurrent_threads_per_session`
   в `.codex/config.toml` при доверенной конфигурации проекта.
4. Основной агент проверяет ссылки, выводы и привязку к SHA, объединяет дубли
   и решает расхождения по доказательствам. Он отвечает за разрешённые правки
   и проверки, `$pr-preflight` и передачу PR на внешнее независимое review.

### Полномочия review

Роли используют модель, reasoning effort, sandbox и approvals родительской
сессии. Они отключают apps, plugins, memories и запрос дополнительных
разрешений, сохраняя чтение через shell и доступ к существующим Skills.
MCP наследуется от родителя. Для проверяемого режима чтения используйте
родительскую сессию `--sandbox read-only` с `approval_policy = "never"` и без
write-capable MCP, apps или plugins. Указание профиля ограничивает поведение
агента. Файловые ограничения задаёт sandbox родителя. При недоступном GitHub
передайте CI Reviewer обезличенные метаданные run и выдержку из gate, полученные
на чтение. [Руководство Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

### Отчёт subagent

Поля отчёта: агент, тип проверки, Repository / PR / полный HEAD, проверенная
область, источники и файлы, проверенные факты, Findings, доказательства и сценарии
воспроизведения, непроверенные области, итог **Blocked / Issues Found / No Issues Found**.

Для Findings используйте **Blocker / Major / Minor**. Дайте путь и проверенную
строку или символ, нарушенный контракт, причину, последствия, условия и вариант
исправления. Отмечайте «рабочее дерево» для локального diff. Сценарий для
будущего теста остаётся предложением до фактического прогона.

## Локальный Stop hook

В CLI под Linux/WSL Workflow-04 запускает advisory-проверку `git diff --check` и
`git diff --cached --check` при `Stop`. Она проверяет staged и unstaged пути
исходников и документации, которые попадают в область пилота. Для изменённых
Markdown-файлов предлагает ручной запуск `python3 scripts/check-doc-links.py`.
Скрипт ссылок читает дерево проекта и цели локальных ссылок, поэтому его
следует запускать осознанно в рабочей копии с допустимыми данными.

После проверки исходников в доверенном проекте откройте `/hooks`, выберите
проектный Stop и подтвердите текущую версию. Повторяйте проверку после изменения
определения. Для отключения используйте `/hooks` или `codex --disable hooks`.
При обновлении скрипта обновите его SHA-256 в определении, чтобы trust относился
к проверенным байтам. Команда вычисления — `sha256sum scripts/codex_hooks/check_changes.py`
на LF-копии. Хэш связывает launcher с версией скрипта. Права задаёт sandbox.

`WARN` содержит путь и причину. `ERROR` означает технический сбой.
`SKIP` указывает причину пропуска или ручную проверку. Тихий вывод возможен
при чистом diff, неприменимости проверки, выключенном или недоверенном hook.
Для воспроизведения выполните две команды Git выше из корня. Инженерные Skills,
специализированный review и GitHub checks применяются по обычному workflow.
[Контракт Codex Hooks](https://learn.chatgpt.com/docs/hooks) ·
[Результаты и границы независимой runtime-приёмки](WORKFLOW_04_VALIDATION.md).

## Оценка workflow

Перед очередным изменением маршрутизации, Skills, профиля или hook используйте
[аудит контекста](CONTEXT_AUDIT.md) и [сценарии оценки](EVALUATION.md).
Для малых задач выбирайте только нужные шаги. При возобновлении повторно
проверяйте актуальность SHA и применимость результатов, используя ссылки
на уже прочитанные разделы. Для расширения набора ролей или hooks требуется
наблюдаемая добавочная польза. Любая внешняя интеграция требует отдельного
решения владельца. Оценочные прогоны проходят в изолированных копиях.
