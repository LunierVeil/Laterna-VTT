# Будущая проверка CLA на GitHub

Соглашение и процесс находятся на рассмотрении. Подписания сейчас нет.
Этот документ описывает настройку после отдельных решений владельца
о вступлении CLA в силу, подключении приложения и, если понадобится,
обязательности проверки.

## Выбор инструмента

Для ограниченного пилота подходит размещённый сервис CLA Assistant. Он
связывает репозиторий с GitHub Gist, предлагает подписать текст через
GitHub-аутентификацию, обновляет статус PR и показывает подписантов по
версиям текста. Сервис предусматривает CSV-экспорт. Репозиторий поставщика
описывает размещение данных в Azure Cosmos DB в Европе. Перед выбором
нужно подтвердить актуальные условия сервиса, доступность, фактическое
хранение и удаление данных и назначить ответственного за реестр.
[Панель CLA Assistant](https://cla-assistant.io/) · [GitHub App](https://github.com/apps/cla-assistant) · [Документация сервиса](https://github.com/cla-assistant/cla-assistant)

Альтернатива — ручное принятие через закрытый реестр с теми же полями и
проверкой правообладателей. CLA Assistant Lite через GitHub Actions умеет
записывать подписи в отдельный приватный репозиторий, но его upstream
архивирован, а типовая настройка требует прав записи. Для пилота выбран
размещённый вариант при условии проверки поставщика. Ручной режим подходит,
если условия сервиса или поддержка корпоративных вкладов не пройдут проверку.
[Документация CLA Assistant Lite](https://github.com/contributor-assistant/github-action)

## Настройка после утверждения

1. Владелец утверждает финальный текст с юридическим именем получателя,
   идентификатор редакции, дату вступления в силу, канал подтверждения
   полномочий и уведомление об обработке данных. Опубликовать текст в
   репозитории и скопировать его без изменений в выделенный Gist. Сверить
   содержимое и сохранить permalink на ревизию Gist, SHA коммита файла и
   SHA-256 точного текста. Публичный Gist содержит только текст соглашения.
2. После разрешения на установку открыть карточку GitHub App, сверить
   издателя и запрошенные права. Сначала подключить приложение только к
   тестовому репозиторию. В панели CLA Assistant связать его с Gist,
   проверить фактический текст, показанный перед принятием, и имя статуса.
   В отдельном тестовом PR проверить отказ без принятия, успех после явного
   согласия, добавление второго автора и смену HEAD, новый текст и прежнее
   принятие, форк и корпоративный случай. Для теста использовать
   однозначно обозначенный демонстрационный текст и тестовые записи.
3. После разрешения на пилот для Laterna связать Gist только с нужным
   репозиторием. При открытии или обновлении PR выявлять авторов и
   правообладателей. При отсутствии подтверждения отправлять ссылку на
   точный текст и уведомление об обработке данных. После явного принятия
   и проверки всех правообладателей связывать запись с PR. Если автор
   открыл PR до принятия, получить явное подтверждение, что согласие
   охватывает перечисленные материалы из этого открытого PR. Сервис
   обновляет свой статус. Перед включением вклада сопровождающий
   подтверждает применимость записи к актуальному HEAD.
4. Пилот проходит с необязательным статусом. Добавление статуса в
   required checks или ruleset требует отдельного явного разрешения,
   после проверки поведения и корпоративных исключений. Отключение
   проверки и переход на ручной учёт должны сохранять архив ранее
   подтверждённых версий и вкладов.

## Авторы, документы и версии

- Перечислить все коммиты PR, проверить GitHub-авторов, трейлеры соавторов
  и заявление в описании PR. Учитывать пагинацию и ограничения API для
  больших PR. Зелёный статус приложения подтверждает лишь результат по
  данным сервиса. Добавление коммитов, rebase и изменения состава
  правообладателей требуют повторной сверки. Для неподтверждённых авторов,
  ботов, неполных или противоречивых данных использовать ручную проверку
  происхождения. У бота устанавливать правообладателя материала.
  [GitHub REST API, коммиты PR](https://docs.github.com/en/rest/pulls/pulls#list-commits-on-a-pull-request)
- GitHub-аккаунт связывает действие с учётной записью, но не удостоверяет
  юридическую личность, соавторство или полномочия представлять компанию.
  Для корпоративного вклада получить подтверждение от уполномоченного
  представителя по закрытому каналу. Связать его с компанией, охваченными
  авторами, PR или перечнем материалов и редакцией CLA. При расхождении
  между статусом сервиса и ручной проверкой вопрос решает сопровождающий.
- Перед сменой текста сохранить прежнюю редакцию, экспорт и список
  охваченных вкладов. Опубликовать новую редакцию с новым идентификатором,
  датой и ссылкой на точную ревизию Gist. Проверить, что сервис предлагает
  принять именно новую редакцию для последующих вкладов, а старые записи
  по-прежнему можно сопоставить с прежней. Для старых вкладов с
  недостаточными правами оформлять отдельные разрешения.

## Реестр и персональные данные

Хранить в закрытом реестре минимально необходимое подтверждение принятия
(источник записи или экспорт, время UTC, стабильный GitHub ID и логин,
если доступны, версия и хеш текста, репозиторий, PR, проверенный HEAD
и коммиты или перечень покрытых материалов). Корпоративное подтверждение
хранить с ограниченным доступом и привязкой к записи. Если в экспорте
отсутствуют необходимые поля, добавить ссылки и сведения вручную до
принятия вклада. При недоступности сервиса использовать утверждённый
ручной порядок.

До пилота определить ответственного за данные, применимые основания
и цели обработки, получателей, условия передачи данных, сроки хранения
и удаления, порядок доступа, исправления и реагирования на запросы.
Доступ к реестру и экспортам ограничить ответственными, настроить
защищённые резервные копии и проверить восстановление. Публичные PR,
ветки, Gist и артефакты CI не подходят для хранения подписей и документов
о полномочиях. Перед принятием предоставить участнику эту информацию и
контакт владельца.
