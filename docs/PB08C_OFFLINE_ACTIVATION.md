# PB-08C · Offline Copy Upgrade with Explicit Activation

Linux-профиль и кандидат Windows NTFS для независимого review в [Draft #100](https://github.com/LunierVeil/Laterna-VTT/pull/100).
[Managed Cutover](PB08C_DURABLE_CUTOVER.md) и его PoC сохранены как исследования.
Условия #49, включая Windows и испытания после внезапного выключения, действуют
до полной приёмки.

## Профиль и точки входа

Поддерживаемый начальный сценарий использует отдельную установку Beta и известную
историческую Linux Alpha с данными в серверном каталоге. Исходник, цель,
приватный каталог состояния и установки лежат на одном проверяемом локальном
mount. Известный Linux launcher и конфигурация исторического backend сверяются
с версией [4d2797d4](https://github.com/LunierVeil/Laterna-VTT/commit/4d2797d4589d42c11ac7e6fb6b13d338d011190f).
Оператор останавливает Alpha и внешние писатели, включая запущенные под другими
учётными записями. Команда проверяет работающие известные точки входа и процессы
в историческом дереве. Она архивирует `laterna.sh` и пакет `server/app` отдельными
атомарными переносами в приватный каталог состояния. Каждый каталог источника и
назначения синхронизируется до допуска подготовки. Это предотвращает случайный
запуск известных entrypoints после вывода установки из эксплуатации. Произвольные
копии программы, внешние писатели и намеренный обход оператором находятся вне
модели. Сама SQLite Alpha, uploads и ключ остаются на месте, PB-07 добавляет
служебный source fence. DataHome или код между томами не переносится автоматически.

Состояние установки хранится рядом с каталогом приложения в
`.<имя-установки>.laterna-cutover`. Привязка внутри установки позволяет обнаружить
пропажу внешней регистрации и отклонить первый запуск пустого стола. Привязка
сама по себе не разрешает запись. Дополнительно backend требует совпадения
DataHome, файловых путей, тома, идентичностей каталога и SQLite и target fence.
Если регистрация доступна, обычная замена файлов Beta в том же пути не меняет
выбранный DataHome. Перемещение установки или потеря доказательств требует
операторского recovery. Распознавание и устойчивость идентичности тома и inode
после аварийного reboot подлежат проверке на заявляемых конфигурациях.

Команды для **отдельных тестовых копий** из установки Beta:

```bash
./laterna.sh upgrade prepare --source "$ALPHA_SERVER" --destination "$NEW_DATAHOME"
./laterna.sh upgrade status
./laterna.sh upgrade activate
./laterna.sh porthole
```

Дополнительные команды — `upgrade cancel` до активации и `upgrade recover` для
зарегистрированной активной цели. Создание backup выбирает действующую цель.
`backup verify` и `backup restore` остаются доступны для явных изолированных путей,
в том числе при HOLD. Изолированный restore в новое место сам по себе не меняет
активный DataHome. Прямой запуск Beta backend требует явно выбранной цели и
проходит ту же серверную проверку.

## Состояния и commit point

| Состояние | Переход и допуск |
| --- | --- |
| UNREGISTERED | Штатный startup PB-05. Существующие fences блокируют неактивированные копии. |
| PENDING | Регистрация существует. Legacy entrypoints выводятся из эксплуатации. PB-07 получает свежий проверенный snapshot и сохраняет receipt и source fence. PB-08B публикует отдельную цель с target fence. Допуск обоих домов закрыт. |
| CANCELLED | Явная офлайн-отмена проверяет имеющиеся доказательства и отсутствие activation record. Старые fences и файлы остаются. Повтор с новой целью создаёт новый ID. При существующем source fence используется отдельный проверенный restore и новый PB-07 snapshot, без открытия исходной Alpha для записи. |
| ACTIVATED | Сначала регистрация необратимо помечается `sealed`. Эта отметка закрывает отмену и повтор и сама не разрешает запуск. Единственный `activation.json` публикуется без замены после проверки исходника, snapshot, receipt, цели и обоих fences. Commit point — успешная синхронизация каталога состояния после публикации уже синхронизированного файла. Backend повторяет барьеры под locks. Только существующая подтверждённая цель получает допуск. |
| HOLD | Потеря решения при `sealed`, утрата регистрации, ошибка барьера, несовпадение путей, занятость, пропавшая цель или незавершённый recovery закрывают запуск. Видимое решение с неопределённым барьером можно подтвердить повторно, без записи противоположного решения. |

Lock установки лежит рядом с приватной регистрацией, вне заменяемого приложения.
Офлайн-команды захватывают его эксклюзивно до регистрации и перед locks DataHome,
для двух домов в порядке target → source. Backend держит разделяемый lock установки
с начала startup, включая незарегистрированный запуск, до завершения lifespan
и закрытия писателей. Storage locks действуют весь lifespan. Разные порты и разные
пути DataHome одной установки не позволяют обойти эксклюзивный офлайн-допуск.
Независимые установки имеют независимые locks. Проверки выполняются до подготовки
хранилища, seed и создания ключа. Отмена после публикации решения запрещена,
даже если последнее подтверждение синхронизации не дошло до оператора.

## SQLite recovery

Штатный startup сохраняет отказ при наличии sidecars. Явный recovery под
блокировками сохраняет полный остановленный комплект SQLite вместе с журналами
в отдельный приватный каталог. SQLite проверяет replay на рабочей копии.
До открытия действующей SQLite для replay синхронизируется checkpoint, который
привязывает ожидаемый результат к попытке и сохранённому комплекту. После
незавершённого recovery обычный startup остаётся закрытым. Повтор сверяет
сохранённый комплект и продолжает тот же recovery.

После replay остаётся та же зарегистрированная SQLite. Проверяются логический
результат, целостность, FK, ревизия, файлы медиа и ключ через storage preflight и
проверяемую резервную копию. SQLite сам завершает обработку rollback journal и
WAL. Оператор не удаляет sidecars вручную. После успеха синхронизируются данные,
backup и снятие checkpoint. При неподтверждённых новых записях, замене или утрате
цели сохраняется HOLD. После проверенного `upgrade recover`, пока backend ещё
не получал допуск к записи, доступен `upgrade rebind --destination "$NEW_DATAHOME"`
для утраченной цели. Доказательство привязано к предыдущему решению и хешу
проверенного backup. Любой последующий допуск к записи сначала долговечно
инвалидирует доказательство. При его утрате или после следующего игрового
запуска старый snapshot можно восстановить отдельно, но активировать его
в этой операции нельзя. Rebind публикует fenced-копию и атомарно обновляет
единственную запись активации. Исходник Alpha и его backup остаются архивом.

## Windows NTFS

Общий автомат использует платформенные Win32 locks, идентичность тома и объекта,
проверку фиксированного NTFS и ACL, запрет reparse points, публикацию без замены
и явные барьеры файлов и каталогов. Windows-ветка архивирует известные
`laterna.bat`, `laterna.ps1` и исторический пакет backend. Режим Profile
использует локальный профиль, управляемая цель Portable находится вне
заменяемого дерева ZIP. Для кандидата проверяется один локальный том,
без вывода о сокращении окончательной платформенной матрицы.

PowerShell принимает `-Action Upgrade -Upgrade Status|Prepare|Activate|Cancel|Recover|Rebind`.
Prepare принимает абсолютные `-AlphaServer` и `-Destination`; Rebind принимает
`-Destination`. При запуске выбранная активная цель проходит backend admission.
До доказательства долговечности статический Windows gate закрывает запись.
Вызовы `MoveFileExW` с write-through и `FlushFileBuffers` являются частью
кандидатного протокола. Неуспешный барьер завершает операцию без выдачи допуска.

## Воспроизводимая приёмка

Штатный Windows smoke остаётся обязательным и проверяет запрет Alpha upgrade
на пакетном кандидате. Для отдельной нативной квалификации запустить
`Windows release` с `candidate_ref` равным точному SHA, `publish=false` и
`pb08c_qualification=true`. Квалификация распаковывает пакет в изолированную
копию, включает допуск только внутри неё и использует подлинные исходники Alpha.
Она проверяет реальный Win32 API. Отзыва или снятия production gate при этом нет.

Для проверки после reboot и остановки VM нужен постоянный локальный диск гостя
(Btrfs/ext4/XFS для Linux, фиксированный NTFS для Windows), рабочая копия репозитория
с историческим SHA и синтетический Windows ZIP точного HEAD. Для Windows
использовать обычного пользователя. Команды выполняются в госте, а вывод
`PB08C_VM_FIXTURE` и `PB08C_VM_CHECKPOINT` сохраняется на хосте.

```text
git fetch --no-tags --depth=1 origin 4d2797d4589d42c11ac7e6fb6b13d338d011190f
python scripts/pb08c-qualification.py --scratch <durable-fixture-parent> --mode Profile --pause <point>
python scripts/pb08c-qualification.py --scratch <durable-fixture-parent> --mode Profile --pause <point> --resume <PB08C_VM_FIXTURE>
```

Для Windows добавить `--zip <candidate.zip>` к первой команде и повторить
с `--mode Portable`. Для каждой пары профиль/точка создать новый fixture.
Доступные точки включают before-source-fence, after-source-fence, staging,
before-target-publish, after-target-publish, activation, after-activation,
confirmed-write, sqlite-rollback, sqlite-wal и recovery. Обе точки SQLite
останавливают процесс в незавершённой пишущей транзакции после отдельного
подтверждённого commit. После перезапуска запускается явный recovery.
На checkpoint выполнить один из трёх сценариев
и повторить второй вызов после возврата управления: завершить только процесс,
перезагрузить гостя штатно, либо выключить VM со стороны гипервизора без
гостевого shutdown. Эти результаты фиксируются отдельно. Скрипт проверяет
хеши Alpha, отсутствие ошибочного запуска, а после активации также текущую
ревизию, SQLite integrity и FK, доступ к выбранному DataHome и подтверждённую
запись там, где она уже была сделана.
