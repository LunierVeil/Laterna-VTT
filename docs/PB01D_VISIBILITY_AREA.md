## Разрешённая граница

Владелец согласовал D01/D02 из [проекта PB-01d](PB01D_VISIBILITY_LIGHTING_DESIGN.md):
точный point LOS сохраняется; начальный контур — событийный, явно приближённый.
**На этапе PB-01d-1 D03–D11 оставались OPEN.** Затем D03–D09 согласованы
для отдельного [ядра Basic Lighting](PB01D_BASIC_LIGHTING.md); D10/D11 и W3
остаются OPEN. В самом модуле области нет света, игровой модели зрения, нового
FoW, авторизации, клиентского renderer или выдачи объектов. `CLEAR` не разрешает
передавать секреты. ROADMAP и LTR-DEC/G1–G6 не изменены.

[Модуль](../server/app/visibility_area.py) не вызывается из REST/WS, handlers,
scene service, frontend или AccessPolicy. Он зависит только от стандартной
библиотеки и [точного ядра](../server/app/line_of_sight.py). Изменение старого
ядра — только readonly-проекция `opaque_segments`, не изменение предикатов.

## Внутренний API

```python
from app.line_of_sight import PreparedGeometry
from app.visibility_area import PreparedVisibilityGeometry

source = PreparedGeometry([((50., 0.), (50., 100.))], width=100, height=100)
prepared = PreparedVisibilityGeometry(source)
area = prepared.visibility_area((25., 50.))
# area.quality == "approximate_zero_width"
# area.contour: tuple[tuple[Fraction, Fraction], ...] | None
exact = area.point_sight((75., 50.))  # BLOCKED, через source, не через polygon
```

- Подготовка неизменяема, копирует координаты; повторно используется для разных
  наблюдателей в пределах **одного snapshot**. Нет глобального кеша, идентификатора
  кампании или утверждения актуальности. После изменения стены/двери нужен новый
  `PreparedGeometry`, как в PB-01c. Старый результат остаётся старым снимком.
- `event_points` содержит точные рациональные координаты событий;
  `unique_segment_count`, `intersection_point_count`, `candidate_pair_count`
  помогают измерять действительную сложность входа, включая пересечения в концах.
- `VisibilityArea` хранит копию observer, `state`, `quality`, `contour`,
  `direction_count`, `ignored_zero_length`. При READY число поисковых лучей равно
  `2 * direction_count`; проекции на границы ячеек вычисляются отдельно.
- Невалидный наблюдатель вызывает `ValueError` точного ядра. В пределах его
  `epsilon` от препятствия возвращается `OBSERVER_ON_OBSTACLE`, `contour=None`:
  это диагностическое состояние, а не нормальная пустая область. Токен не двигается.
- `area.point_sight(target)` и `prepared.point_sight(observer, target)` делегируют
  старому точному ядру, включая epsilon и диагностику нулевых стен. Метода
  `contains` и нового разрешения на раскрытие объектов нет.

## Алгоритм

1. Подготовка получает opaque-сегменты существующего `PreparedGeometry`.
   Нулевые сегменты уже исключены и посчитаны точным ядром. Дубли и обратные
   сегменты канонизируются только для построения контура.
2. Неизменяемый BVH с точными AABB сокращает поиск пересекающихся пар. Все концы,
   все непараллельные пересечения (включая T/X) и четыре угла сцены — события.
   У коллинеарных перекрытий достаточно всех концов; бесконечный набор точек
   перекрытия не материализуется. Пересечения не округляются до float.
3. Для наблюдателя направления на события нормализуются в целочисленные пары.
   Порядок задаётся полуплоскостью и точным векторным произведением. Нет `atan2`,
   фиксированного числа лучей, углового шага, `±delta` или слияния близких углов.
4. Между соседними направлениями выбирается одно точное внутреннее направление.
   Так как все концы и пересечения представлены, ближайшая центральная линия
   стены внутри этой открытой угловой ячейки не меняется. BVH/slab-проверки и
   пересечение ray/segment используют Fraction, без отсечения по округлённым float.
5. Для каждого события сохраняются левый предел, точный контакт и правый предел.
   Они вычисляются проекцией уже найденных стен на направление события, без
   малого углового сдвига. Точный контакт нужен для изолированной радиальной стены.
   Удаляются только последовательные дубли и повтор замыкающей вершины.
6. Граница сцены ограничивает луч, но **не становится стеной**: наблюдатель может
   стоять на границе или в углу. Для наружной угловой ячейки её предел — observer,
   в том числе когда её край направлен вдоль границы сцены.

Все решения о пересечениях центральных линий точны для переданных binary64
координат. Это не доказывает эквивалентность контура epsilon-геометрии.

## Точность и топология

- `quality="approximate_zero_width"` обязательно присутствует. Контур относится
  к стенам нулевой толщины; точный LOS блокирует также epsilon-окрестности стен.
  **Ни безопасная внутренняя, ни внешняя граница не гарантируется.** Например,
  луч в `epsilon/2` от конца стены может лежать внутри контура, но быть BLOCKED.
- Вершины — Fraction; преобразование в float, упрощение и визуализация не входят
  в модуль. Клиенту контур не отправляется. Дополнительный допуск не вводится.
- При касании изолированного радиального препятствия контур делает возврат по
  одному лучу. Это weakly-simple граница с радиальными повторами, **не обещание
  простого polygon**, пригодного для произвольного triangulator/union.
- Очень короткие, но ненулевые сегменты, субнормальные числа, узкие щели и почти
  параллельные линии сохраняются. Большие знаменатели Fraction могут быть дороги.
- Если нарушен инвариант угловой ячейки, выбрасывается `ArithmeticError`;
  подстановка всей сцены или CLEAR запрещена. Нет скрытого усечения работы.
- Обычные двери уже обработаны PB-01c: open прозрачна, closed/locked непрозрачны
  независимо от blocks_sight. Сам модуль не читает ORM и не выбирает оптику окон.

## Сложность и ограничения производительности

Пусть N — число уникальных ненулевых сегментов, C — число пересекающихся AABB,
K — число точек пересечений, E — число различных направлений событий.

- Нынешняя median-sort BVH строится за `O(N log² N)`, память дерева `O(N)`.
- Подготовка событий проверяет C пар точной арифметикой. В худшем случае C и K
  квадратичны, BVH этого не устраняет. Сами углы не дискретизируются ради лимита.
- Сортировка направлений `O(E log E)`, `2E` запросов ближайшего препятствия.
  BVH ускоряет типичный запрос, но худший случай остаётся `O(N)` на луч,
  всего `O(EN)`, не гарантированный real-time sweep. Выход `O(E)`.
- Стоимость операций Fraction зависит также от разрядности числителей и
  знаменателей; оценка только по N не является бюджетом CPU.
- Жёсткие лимиты N/K/E, cancellation, scheduler и production-бюджеты **не выбраны**
  (D10 OPEN). Поэтому не подключать расчёт к event loop, массовым LOS/свету/FoW.
  Нет нового persisted data или нового значения emits_light/vision_range.

## Проверки

[Тесты](../server/tests/test_visibility_area.py) проверяют аналитические площадь
пустой/разделённой комнаты и границы сцены; X/T, перекрытия, радиальное касание,
нулевые и субнормальные стены, узкую щель, почти параллельные линии до 8192 px,
масштабирование, неизменяемость и порядок/разворот сегментов.

Независимый линейный ray/segment oracle сравнивается с BVH. Независимый test-only
point-in-polygon сравнивается с точным LOS на детерминированных внутренних
случайных точках; отдельный тест **фиксирует несовпадение** в epsilon-полосе.
Все десять синтетических сцен PB-00 сравнивают point-запросы результата с
Fraction-эталоном PB-01a. Для window fixture проверены обе гипотезы opaque input;
это тест входных сегментов, не выбор W3. Двери проверены через существующий
`prepare_scene_geometry` без DB/API и новой модели данных.

## Воспроизводимый benchmark

```bash
server/.venv/bin/python scripts/benchmark_visibility_area.py --samples 3
```

[Скрипт](../scripts/benchmark_visibility_area.py) выводит JSONL в stdout, никаких
пользовательских данных или БД. Профили: grid (короткие раздельные стены), occluded
(тот же набор за сплошной стеной), crossings (N/2 раздельных X-пересечений).
Каждый содержит 200/2000/10000 уникальных стен в сцене 8192×8192; observer=(100,4000).
Это синтетические нагрузки, не гарантия для всех карт с тем же N.

Три timing-повтора; median и nearest-rank p95 (при трёх повторах p95 = максимум).
Общий warmup на 20 стенах, затем один нетаймируемый контур для счётчиков каждого
случая перед тремя замерами. GC включён, предварительный collect вне таймера.
Память измерена **отдельными** tracemalloc-прогонами: peak новых Python allocations
для каждой фазы, не RSS, не сумма фаз, не память всего процесса/GPU. Исходный
PreparedGeometry уже живёт при замере подготовки; оба snapshot живут при замере
контура. В retained/peak может входить память временных кешей Python.

Измерено в Cloud Environment: Python 3.12.14, Linux x86_64, AMD EPYC 9V74,
5 доступных логических CPU; реализация однопоточная. Timing-проходы завершены
до повторного полного тестового набора; memory-проходы отделены от timings.
Это малая выборка в общей облачной среде, не гарантия p95 latency/SLA.

Выводы измерения:

- На grid 10000 контур занимает 26.95 s median (27.09 s p95), на crossings —
  29.33 / 29.85 s. Это **не интерактивный бюджет**. Добавление источников или
  наблюдателей умножит стоимость. Подключение к игровому loop не разрешено.
- На occluded 10000 — 15.07 s median: BVH ускоряет ближайшее пересечение, но
  события за первой преградой не отбрасываются. Нет тайного сокращения числа лучей.
- Сцена crossings содержит 5000 раздельных X, не все попарные пересечения 10000
  стен. Худший квадратичный arrangement не ограничен этими цифрами; общая вершина
  40 стен отдельно проверена тестом. D10 остаётся отдельным решением до интеграции.
- Source и подготовку можно переиспользовать, но смена стены/двери требует нового
  snapshot. Кеширования устаревшей геометрии и автоматического invalidation нет.
- Нет утверждения об отсутствии утечек памяти, полной RSS или долговременном
  runtime: это фазовые allocation peaks одного вызова, не стресс-тест renderer.
