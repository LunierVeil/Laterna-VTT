## Согласованные решения и scope

D03–D09 [проекта PB-01d](PB01D_VISIBILITY_LIGHTING_DESIGN.md) согласованы владельцем
**для изолированной вычислительной реализации**:

| Решение | Реализовано | Граница |
| --- | --- | --- |
| D03 | Бинарные LIT/UNLIT и логический OR источников | Нет RGB, яркости, falloff, смешивания или D&D rules |
| D04 | Явный ambient `none` / `full` | Нет default, записи в Scene или автоматического выбора |
| D05 | Явная конечная позиция и конечный положительный radius в px | Нет token anchor, persisted источников, нулевого радиуса как выключателя |
| D06 | Старые emits_light/vision_range не читаются и не мигрируют | Их исторические значения не становятся радиусом/ambient |
| D07 | Existing PreparedGeometry, включая обычные стены/двери PB-01c | W3 OPEN; нового window adapter нет |
| D08 | Ошибочный ввод — явная ошибка; источник на препятствии — UNAVAILABLE всей field | Нет частичного положительного результата, пропуска плохой лампы или fail-open |
| D09 | G и L возвращаются отдельно | Нет final Visible, darkvision или shared vision |

**D10/D11 остаются OPEN до runtime-интеграции.** Не изменены движение, БД,
сохранения, существующие REST/WS, frontend, AccessPolicy, FoW, ROADMAP и правила
D&D. Модуль не подключён к игровому циклу и ничего не отправляет игрокам.
[Approximate contour PB-01d-1](PB01D_VISIBILITY_AREA.md) не используется.

## API и инварианты

[lighting.py](../server/app/lighting.py) зависит только от стандартной библиотеки
и [точного LOS](../server/app/line_of_sight.py). Точный модуль не изменён.

```python
from app.line_of_sight import PreparedGeometry
from app.lighting import Ambient, LightingField, LightSource, LightState

g = PreparedGeometry([((50., 0.), (50., 100.))], width=100, height=100)
torch = LightSource(g, position=(25., 50.), radius=100.)
field = LightingField(g, [torch], ambient=Ambient.NONE)
light = field.point_light((75., 50.))  # UNLIT: лампа за стеной
geometry = field.point_sight((75., 25.), (75., 50.))  # CLEAR: другой вопрос
assert light.state is LightState.UNLIT
```

- `LightSource`: frozen/slots, копия `position`, `radius`, вычисленное `state`:
  READY или ON_OBSTACLE (`source_on_obstacle`). Это готовность источника
  в конкретном snapshot, **не новая настройка enabled/disabled**. Радиус не имеет
  default. Невалидные координаты/радиус вызывают `ValueError` до положительного
  результата. Неправильный тип geometry — `TypeError`.
- Источник на препятствии или в пределах его epsilon не двигается. Его
  `point_light()` возвращает `UNAVAILABLE` даже для цели вне радиуса. Остальные
  источники/ambient не могут скрыть эту диагностику.
- `LightingField`: frozen/slots, eagerly фиксирует весь iterable источников в tuple,
  проверяет типы и binding **всех** элементов. Ошибка позднего элемента/итератора
  не создаёт частично готовый объект. `ambient` — обязательный keyword аргумент;
  допускаются enum или точные строки `none`/`full`, не None/auto/bool.
- Каждый источник должен ссылаться на **тот же объект** PreparedGeometry.
  Даже равная по координатам другая instance отвергается. Это узкий локальный
  инвариант одной геометрии, не доказательство свежести данных или D11 read consistency.
- `unavailable_source_indices` содержит все индексы источников на препятствии.
  Если он непуст, любой валидный запрос освещения возвращает UNAVAILABLE **до**
  ambient full, радиуса, положительного ответа другой лампы или short-circuit OR.
- `point_light(target)` возвращает LightResult: LIT/UNLIT/UNAVAILABLE и
  `ignored_zero_length` исходной геометрии. Диагностика не умножается на число ламп.
  Невалидная цель — `ValueError`, даже при ambient full или вне всех радиусов.
  Использовать `.state`, не truthiness объекта результата.
- `point_sight(observer, target)` возвращает исходный SightResult: CLEAR/BLOCKED/
  OBSERVER_ON_OBSTACLE. Его ответ независим от освещения. Свет может быть LIT,
  когда обзор BLOCKED; обзор может быть CLEAR, когда UNLIT. Ни один ответ не
  разрешает выдачу защищённых объектов, медиа или геометрии.

## Численная модель

Позиции и радиус — конечные native int/float, нормализованные до binary64,
без bool/строк. Позиции находятся в существующих границах сцены. Сетка, камера,
футы, свойства токена или системы НРИ не участвуют.

Выбранная внутренняя геометрическая граница круга — **включительно**:
`dx² + dy² <= radius²`. Никакого дополнительного radius-epsilon нет. Fraction
строится **до вычитания координат**, сравнение квадратов не использует sqrt и
не переполняется/не обнуляется при очень большом/субнормальном положительном
радиусе. Это точность относительно переданных float, не восстановление исходного
десятичного замысла. Новые продуктовые numeric limits не выбраны (D10 OPEN).

Сначала проверяется радиус: цель вне круга UNLIT без луча. Внутри круга LIT
возможен только при `PreparedGeometry.point_sight(source.position, target)=CLEAR`.
Касание стены/конца, закрытая/запертая дверь и epsilon-окрестности используют
старый точный LOS. При ambient full valid field вся сцена освещена; стены всё
равно ограничивают **геометрический обзор**. Ambient не является неизвестной лампой.

Локальный validator позиции повторяет native-number/bounds-контракт LOS, поскольку
ambient/radius могут обходить LOS и всё равно обязаны проверять цель. Приватные
helpers точного ядра не импортируются, полный scan стен ради валидации не делается.
Regression tests проверяют совпадение отказов по ошибочным позициям.

## Snapshot и стоимость

Геометрия, источники и field неизменяемы; нет глобального кеша или DB read.
Изменение двери/стены требует новой PreparedGeometry **и новых привязанных
источников**. Перемещение источника/изменение радиуса — новая LightSource/field,
без мутации старого результата. Старый объект остаётся старым snapshot; он не
получает свежесть автоматически. Нет готового server bundle для реальных токенов.

Для S источников и N стен: подготовка источников содержит S проверок позиции
точным LOS, в худшем случае O(SN); field проверяет O(S) bindings. Один запрос
с ambient none — до S проверок радиуса и до S точных LOS, worst-case O(SN),
с ambient full — O(1) после полной подготовки. OR останавливается на первой
освещающей лампе, поэтому порядок влияет на стоимость, но не на бинарный ответ.
Стоимость Fraction зависит от разрядности; это не SLA. Нет нового area/polygon
union, обхода всех пикселей или кадровой анимации. Массовую runtime-нагрузку и
бюджеты ещё нужно утвердить; microbenchmark ниже этого не заменяет.

## Тесты

[Новый набор](../server/tests/test_lighting.py) проверяет пустую сцену, факел,
радиус и его границу, открытые/закрытые/запертые двери через существующий PB-01c
adapter, OR/пересечение/перестановку источников, ambient, глобальный unavailable,
нулевые стены, плохие значения, позднюю ошибку iterable, неизменяемость и snapshot.

Детерминированные случайные сцены и десять fixtures PB-00 сравниваются с
независимым Fraction-эталоном PB-01a. Для window fixture обе гипотезы opaque input
проверяются **только как тестовые сегменты**, это не выбор W3. Свет/авторизация/
ручной FoW fixture не смешиваются. Дополнительный тест подтверждает, что точка
внутри приближённого zero-width контура не становится LIT в epsilon-полосе стены.

## Benchmark

```bash
server/.venv/bin/python scripts/benchmark_lighting.py --samples 3
```

[Скрипт](../scripts/benchmark_lighting.py) использует только synthetic fixtures,
без БД, source token fields и пользовательских данных. Профили: пустая сцена;
две комнаты с открытой/закрытой дверью; PB-00 complex (200 стен); дополнительный
stress-2000 в сцене 8192×8192. Источники заданы явно: 1/4/8, target-точек 100,
seed фиксирован. Поля старых токенов не превращаются в источники.

Медиана/p95 по трём замерам (nearest-rank p95 = максимум из трёх); перед замерами
каждого случая есть один нетаймируемый проход. GC включён, предварительный collect
вне таймера. Подготовка geometry, sources, field и 100 point queries измеряются
раздельно. Memory-прогоны отделены от timing: tracemalloc peak **новых Python
allocations**, не RSS, не сумма фаз, не GPU и не доказательство отсутствия утечек.
При query memory готовые geometry/sources/field уже живут; tuple из 100 результатов
включён в замер. Малая выборка в общей cloud-среде не является latency/SLA.

Измерено: Python 3.12.14, Linux x86_64, AMD EPYC 9V74, 5 доступных логических CPU;
код однопоточный. Полные тесты запускались после окончания timing-прогонов.

- В типичной PB-00 complex (200 стен) 8 источников/100 точек: 10.68 ms median,
  11.87 ms p95. В stress-2000: 130.02 / 134.51 ms. Это разные сцены и распределения
  целей, не гарантированное линейное масштабирование или сравнение качества карт.
- Закрытая дверь заставляет проверять больше источников перед UNLIT, тогда как
  первая освещающая лампа позволяет short-circuit OR. Дополнительные лампы могут
  заметно повышать стоимость. Порядок источников влияет на время, не на ответ.
- Ambient full дешёв только **после** полной валидации источников. Источник на
  препятствии не даёт положительного ответа и при full; это отдельно проверено.
- Измерены точечные пакеты, а не контур освещения, кадры, сетевой путь, динамическое
  FoW или тысячи наблюдателей. Нет утверждения интерактивной производительности.
  Худшие расположения и большие Fraction inputs требуют отдельной нагрузки (D10).

## Вопросы перед PB-01d-3 — не реализация

1. **D10:** какие N стен/S источников/Q запросов и CPU/memory/latency budgets
   считать допустимыми? Как выражать отмену/исчерпание бюджета явным unavailable,
   без частично положительного результата? Пределы не выводить из одного benchmark.
2. **D10:** где исполнять расчёт, как объединять/отменять устаревшие задания и
   избежать блокировки event loop? Offload сам по себе не уменьшает стоимость.
3. **D11:** как получить geometry и реальные источники одним доказанно согласованным
   read-context, без JOIN walls×sources и смешивания версий после door/source move?
   Объектная identity этого модуля не заменяет read-transaction/version contract.
4. **D11:** какие version/freshness/lifetime checks применять к результату перед
   будущей композицией? Нет разрешения использовать долгоживущий старый snapshot
   как authorization lease, даже если он immutable.
5. Реальные token/map source bindings, enabled/disabled, numeric limits и persistence
   требуют отдельного scope. D06 по-прежнему запрещает автоматически трактовать
   emits_light/vision_range; при новом persisted data сначала migration gate.
6. W3, darkvision, personal/shared vision, FoW и серверное раскрытие объектов остаются
   отдельными решениями. G/L не объединять в разрешение доступа; чувствительные
   источники/геометрию не отправлять клиенту без будущей PB-02 policy/projection.

PB-01d-3, lighting runtime, Ready/merge этой реализации и Windows release не
запускаются автоматически. Следующий шаг — независимое review конкретного HEAD.
