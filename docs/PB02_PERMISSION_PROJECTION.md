# PB-02: первый функциональный срез permission/projection

## Scope и проверка в игре

Это серверный код в работающем приложении, а не завершённый игровой LOS.
При включённом экспериментальном флаге существующие слой ГМ и ручной FoW
определяют выдачу токенов в REST/WS и доступ к связанным изображениям.
Переключение слоя ГМ отзывает токен и последующие запросы его приватного
изображения. Видимый портрет NPC не открывает остальные вложения его листа.

**NPC за обычной стеной пока не скрывается автоматически.** Двери в этом
срезе не меняют выдачу NPC; ambient/full и новые источники не подключены.
Окончание PB-02 требует полного серверного и браузерного сценария
«ГМ + два игрока + NPC за дверью» и отрицательных проверок утечек.

База требований: `LATERNA_BETA_UNIFIED_MASTER.md`, часть IV §3, PB-02/W1–W2
(предоставленный владельцем MASTER/backlog),
[LTR-DEC-003 и G2](BETA_DECISIONS.md), [архитектура](ARCHITECTURE.md).
Исторический PB-03 — клиентский свет/FoW, PB-04 — редактор стен/дверей/окон;
они не подменяются новым I-блоком. Старое предложение PB-03 использовать
`emits_light` не отменяет последующий запрет D06 на неявное source mapping.
Owner Decision о переходе к игровому срезу имеет приоритет над отдельными
предварительными исследованиями scheduler/Windows benchmark.

## Запуск на Linux

Из корня проекта, с обычным окружением разработки из
[DEVELOPMENT.md](DEVELOPMENT.md):

```bash
LANTERNA_EXPERIMENTAL_VISIBILITY=1 ./dev.sh
```

Флаг должен попасть именно в процесс backend. При прямом запуске из `server`:

```bash
LANTERNA_EXPERIMENTAL_VISIBILITY=1 .venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

По умолчанию флаг выключен: legacy `/uploads` остаётся публичным, как в
characterization PB-00. Это известное ограничение, не безопасный production
default. Тест PB-00 не удалён и не переобозначен как исправленный для всех запусков.
Некорректное значение флага останавливает запуск вместо тихого отключения.

Минимальная ручная проверка этого PR: войти ГМ и двумя игроками, загрузить
NPC-портрет и отдельное изображение во вложение его листа, разместить токен.
Убедиться, что видимый портрет доступен игрокам, а вложение — только ГМ;
перевести токен на слой ГМ, проверить удаление токена и отказ по уже известному
URL портрета. Не использовать для этого пользовательские приватные данные.
Обычная подложка активной сцены может передаваться целиком согласно LTR-DEC-003.

## Серверные инварианты

- `recipient_projection` объединяет существующие правила GM/manual FoW:
  владелец видит свой токен в ручном тумане, но слой ГМ скрывает его от игроков.
  Та же функция используется snapshot, событиями и drag preview.
  Скрытые участники боя и указатель текущего скрытого участника также
  фильтруются. Знание ID не даёт игроку права менять скрытый токен, дверь
  или строку инициативы. Существующие owner/GM проверки выполняются дополнительно.
- Доверенный получатель определяется сессией, текущей ролью и кампанией из БД,
  не полями клиента. В экспериментальном однокампанейном режиме основной является
  самая ранняя кампания (`created_at`, затем `id`); REST и ACL выбирают её одинаково.
  Это не реализация переключателя кампаний или multi-tenant hosting.
- Перед отправкой в подписанный WS проверяется актуальность сессии/роли/сцены;
  устаревшее соединение получает `auth_required` и закрывается. Входящие команды
  также проверяются. Безопасные campaign/presence controls допускаются при
  уходе со старой сцены, иначе сломается существующее переключение сцены.
- Snapshot и media ACL читаются в собственных физических SQLite read-транзакциях,
  включая legacy transaction mode. ORM identity map не используется как
  доказательство актуальности сессии. Отмена запроса не оставляет read lock.
- `/uploads` проверяет cookie до выдачи файла, включая HEAD/Range/conditional GET.
  Отказ не содержит данных объекта; разрешённый ответ имеет `private, no-store`
  и `Vary: Cookie`. Путь ограничен каноническими именами текущего upload API.
- Разрешение следует из актуальной разрешённой ссылки: подложка активной сцены,
  видимый токен, собственный лист либо портрет листа видимого токена. Видимость
  портрета не даёт права читать JSON листа или его прочие изображения.
- Один файл может использоваться несколькими объектами. Достаточно одной
  разрешённой ссылки: байты публично используемой подложки не становятся секретом
  из-за ссылки скрытого NPC. Идентификатор и DTO скрытого NPC всё равно не выдаются.
- Игрок не может присвоить недоступный приватный URL своему токену/листу.
  Уже разрешённый видимый портрет можно переиспользовать: это существующий
  UI-поток, проверяемый Chromium `Fog images`. Перед commit команды проверяется
  канонический результат handler, включая разобранный импорт и document edits,
  относительно **ранее сохранённых** ссылок, собственных ресурсов и pending grant.
  Отказ откатывает команду без изменения seq и публикации. Неизменённая ссылка
  не требует нового разрешения на прикрепление. Переиспользованный файл сохраняет
  доступ через новую разрешённую ссылку даже после скрытия исходного токена;
  скрытый DTO исходного токена при этом не выдаётся. Это не ретроспективный аудит
  происхождения всех ссылок, уже имевшихся в Alpha-сохранениях.
- Для существующего preview ещё не сохранённого изображения действует временный
  grant только загрузившей сессии/пользователя/кампании. После привязки решают
  ссылки. Grants не переживают перезапуск, не являются новыми persisted ACL.

Временные консервативные ограничения: до 256 кандидатов каждого вида ссылок,
до 1 000 000 UTF-8 байт проверяемого JSON, 1 секунда на media ACL; не более
256 pending grants, срок 600 секунд. Превышение/ошибка/отмена не дают разрешения.
Это не production SLA и не обещание масштабируемости. JSON разбирается вне
asyncio event loop; DB-read и проверка ссылок ограничены, но глобальный admission
и CPU scheduler этим PR не реализуются.
Preview несохранённой загрузки может стать недоступным после 10 минут,
перезапуска или попадания запроса в другой worker. Pending grants рассчитаны
на экспериментальный одиночный backend, а не на распределённую asset library.

## Проверки и оставшиеся ограничения

`server/tests/test_pb02_projection.py` проверяет реальный REST/WS/media путь:
двух игроков, GM layer, manual FoW/owner exception, reconnect/resync,
noop с сохранённым seq, add/remove, приватные вложения, отзыв доступа к media,
Range/HEAD/ETag, session revoke/expiry, чужую кампанию, бюджеты и отмену SQLite read.
Есть отрицательные проверки known-ID команд, скрытых строк инициативы,
перепривязки приватного/видимого портрета и атомарного rollback.
Существующие тесты и строгий browser manifest не ослабляются.

### Исправления review: initial WS publication и REST denial

Initial snapshot и следующий campaign проверяются отдельно до `hub.join()`:
отзыв сессии или смена роли не позволяют отправить уже подготовленный приватный
DTO. Если сессия действительна, но сцена сменилась, старые frames отбрасываются,
а свежий campaign redirect сохраняет SPA navigation. Snapshot → campaign → join
остаются под scene lock; SQLite read sessions закрываются до network send.

`GET /api/scenes/{scene_id}` возвращает единый HTTP 404 с `scene not found`
для отсутствующей/недоступной сцены, включая отказ `scene_snapshot()` после
успешного precheck. Возврат HTTP 200 с error-object удалён. Существующая
PB-00 проверка удаления сцены обновлена на этот более строгий HTTP-контракт.

Детерминированные regression tests используют synchronization barriers без
случайных sleep: revoke/role/scene между capture и каждой initial publication,
защита initial redirect, revoke между REST precheck и snapshot, а также отдельная
DB-запись непосредственно на transport boundary. Это проверка точек актуальности,
не новый универсальный atomic fence для произвольных внешних writers.

Read-транзакция даёт согласованный снимок на время чтения, а не бесконечную
актуальность уже выданного ответа. Этот PR не заявляет атомарного publication
fence относительно произвольного внешнего writer, не отменяет уже скачанные
байты и не объявляет будущие LOS-результаты безопасными для публикации.
Endpoint-specific character projection сохраняется; полноценные G2 материалы,
search, будущая библиотека ассетов и новые форматы ссылок пока не реализованы.
Прикладное расширение ACL потребует добавления соответствующих проверок,
а не автоматической раздачи неизвестных файлов.

## Следующие связанные функциональные PR

1. Текущий: общий permission/projection и закрытие raw-media обхода под флагом.
2. Exact LOS через существующий PB-01 `PreparedGeometry`: наблюдатели игроков,
   выдача NPC, пересчёт при двери/движении, bounded fail-closed, trusted read и
   проверка актуальности перед публикацией, согласованные REST/WS/media.
   Не использовать approximate polygon как источник истины.
3. Завершение игрового вертикального среза: минимальная клиентская интеграция
   при необходимости и Chromium «ГМ + два игрока + NPC + дверь», delayed/stale
   result, reconnect/resync и негативные security-тесты. Допустимо объединить
   пункты 2–3, если diff остаётся безопасным для review.

Критерий завершения — NPC появляется/исчезает при открытии/закрытии двери в
запущенной Laterna на Linux, и скрытые данные не обходят серверную защиту.
Новые схемы, source mapping, автоматический FoW, окна W3 и миграции этим PR
не выбираются. Windows packaging и release не запускаются.
