# PB-03 — визуальный свет и текущий обзор

База: `2034236f94c53740644986bb79b3489b3a1094b7`, после PB-02/#40.
[Issue #44](https://github.com/LunierVeil/Laterna-VTT/issues/44).
Это визуальный игровой срез, не AccessPolicy, не сохраняемая разведка и не PB-14.

## Проверка в игре

На Linux/CachyOS, с зависимостями из [DEVELOPMENT.md](DEVELOPMENT.md):

```bash
LANTERNA_EXPERIMENTAL_VISIBILITY=1 ./dev.sh
```

У ГМ: **Сцены → Настройки → Свет и обзор (экспериментально)**. Выбрать явный
окружающий свет «Полный»/«Нет», добавить источник, указать X/Y и положительный
радиус **в пикселях сцены**, нажать «Применить свет и обзор».
Можно добавить до 15 источников и выключить эксперимент кнопкой. До первого
применения новый слой выключен; автоматической трактовки старых полей нет.

Для ручной сцены нужны два игрока, по одному связанному собственному PC `dnd5e`,
NPC, стена с обычной дверью и несколько комнат. Сначала использовать ambient none
и источник в первой комнате, затем добавить второй источник в другой комнате.
Closed/locked дверь ограничивает свет и обзор; open пропускает. Переместить PC,
проверить NPC, ручной FoW, pan/zoom, reconnect и переключение активной сцены.

**Источники в этом адаптере публичные и временные:** координаты/радиусы доступны
участникам сцены. Они не должны содержать скрытые ссылки/идентификаторы объектов.
Они переживают переподключение, но не перезапуск сервера; удаление сцены/явный reset
их очищают. Никаких новых SQLite tables, persisted JSON или localStorage keys нет.
Это не редактор PB-16 и не модель сохраняемых источников PB-14.

## Вычисление и renderer

- `visual-geometry.ts`: событийные лучи к концам стен, пересечениям и границам
  сцены, с явным пространственным отклонением `1e-4 px` по краям событий.
  Нулевые стены игнорируются, closed/locked door непрозрачна независимо от
  старого `blocks_sight`; open дверь пропускает. Это **приближение**, не точный LOS.
- `visual-worker.ts`: отдельный worker на активный визуальный слой. Geometry
  переиспользуется при движении PC, свет — при неизменных источниках/геометрии.
  Изменение двери инвалидирует геометрию. Нет работы по геометрии на каждом кадре.
- Временные visual budgets: 200 стен, 4096 событий геометрии, 15 источников.
  Выход за пределы/невалидная геометрия/источник на препятствии дают непрозрачный
  результат, а не частично положительное раскрытие. Это не production SLA.
- `visual-layer.ts`: две переиспользуемые Canvas2D поверхности и одна собственная
  Pixi Texture/Sprite. Максимальная сторона маски — 1024 texels. Объединение кругов
  света, ограниченных стенами, пересекается с текущим обзором PC. Ambient full
  убирает только дополнительное ограничение света, не стены обзора.
- Все поверхности находятся в координатах `world`: pan/zoom меняют transform,
  не вычисления маски. Маска затемняет карту, стены и чужие токены. Собственные
  токены остаются сверху для управления; ручной FoW продолжает рисоваться своим
  прежним слоем. ГМ видит затемнение с прозрачностью 35%, без ограничения своим PC.
- Один текущий worker request и один заменяемый pending request. Generation guard
  не применяет устаревшие ответы; нет неограниченной очереди и глобального scheduler.
  При смене сцены прежняя маска выключается, при dispose worker завершается,
  Texture/source уничтожаются, canvas buffers обнуляются. Application/WebGL renderer
  не пересоздаётся при изменении света. [Pixi cleanup](PIXI_STAGE_CLEANUP.md) сохранён.

## Контракт и безопасность

Аддитивное расширение экспериментального snapshot: `scene.visuals` содержит
`settings: {ambient, sources: [{x,y,radius}]} | null` и `observer_id | null`.
Без флага поле отсутствует. Новая команда **только ГМ** `scene.visuals` принимает
`{settings: ...}` либо явный `{settings: null}`. Сервер валидирует поля и текущую
сессию/роль/сцену, меняет только ограниченную память процесса (до 64 сцен), затем
рассылает существующий snapshot с неизменным committed `seq`. Это не новый event,
не write в БД и не изменение seq/cmd_id/base_seq. Старые commands/DTO fields не меняются.

Observer берётся из узкой [policy PB-02](PB02_GAMEPLAY_LOS.md), а не из выбора
клиентом произвольного чужого токена. Ноль/несколько PC, unavailable/busy/timeout
серверного LOS либо недоступная клиенту геометрия дают `observer_id=null`: визуально
остаётся закрытая карта и собственный PC. Нельзя восстанавливать отсутствующие
защищённые стены на клиенте или выбирать W3 по неполному snapshot.

**Серверный точный PB-02 остаётся authority:** отсутствие token/character/media
доступа не заменяется визуальной маской. Клиентская approximation ничего не
разрешает. В этом PR свет также **не ограничивает выдачу DTO**: токен с разрешённым
геометрическим LOS может быть получен, но визуально затемнён из-за отсутствия света.
Для изменения этой серверной policy нужно отдельное решение; здесь не утверждаются
D&D darkvision, personal/shared vision сверх узкого PB-02 или source mapping.
`Token.emits_light`/`vision_range`, PB-01 exact geometry/LightingField и AccessPolicy
не изменены. Обычная карта по LTR-DEC-003 по-прежнему может передаваться целиком.

## Проверки и ограничения

Новые frontend geometry tests входят в `npm test`; backend validation/security
regressions — в полный pytest. Автономный игровой и performance probe:

```bash
cd web
LANTERNA_EXPERIMENTAL_VISIBILITY=1 CHROMIUM_PATH=/usr/bin/chromium \
  node --test tests/browser/visual-lighting.mjs
```

Probe проверяет настоящий WebGL canvas через `readPixels` после render: источник,
две комнаты/дверь, два источника, два игрока, движение PC, manual FoW, pan/zoom,
reconnect, отзыв NPC PB-02, смену сцены и доставку настоящего задержанного worker
ответа после dispose. Performance case использует синтетический PB-00 seed
**30 tokens / 200 walls**, а 15 источников задаёт **отдельно явно**, без mapping
старого emits_light. Отчёт сохраняется вне Git в browser results/performance.json.

Новый probe пока автономен: основной manifest и строгий gate не изменялись.
Full CI актуального test merge выполняется после независимого review/Ready;
Draft skipped jobs не считаются пройденным Full CI. Ручная приёмка владельца
на CachyOS и независимое review точного HEAD остаются обязательными.

Ограничения визуальной точности: raster resolution, сглаженные границы кругов,
float ray intersections и узкие проходы могут давать расхождения у границ. При
скрытой manual FoW геометрии выбран консервативный непрозрачный fallback. Нет
production FPS/SLA, hard CPU isolation и доказанной стабильности общего heap/GPU
memory. Известная проблема Pixi shader cache не объявляется исправленной.
Нет сохранённого Explored, фоновых обновлений выключенной сцены, источников на
токенах, новых D&D rules, windows W3 или расширенного UI PB-04/PB-16.

## Дополнительные regression cases

Проверка границы сцены обнаружила сворачивание контура для источника/observer
точно на внешнем крае: пересечение луча с этой же границей на расстоянии ноль
принималось за препятствие во всех направлениях. Исправление различает луч,
направленный наружу (остаётся на границе), и внутрь (ищет следующую границу).
Добавлены независимые проверки четырёх краёв/углов; правило реальной стены не
менялось. Серверный exact LOS этим исправлением не затрагивается.

Отдельный backend regression сохраняет W3 OPEN: неизвестная оконная геометрия
не превращается в прозрачное окно из-за фильтрации DTO, а отключает визуального
observer. Проверки запрета player-команды, ошибочных источников, unchanged seq,
отсутствия сохранения и legacy flag-off режима сохранены.

## Результат локального финального прогона

Linux, AMD EPYC 9V74, Python 3.12, Node 24, headless Chromium; исключительно
изолированные синтетические DB/uploads. Backend **588 PASS**, frontend unit
**23 PASS**, TypeScript/build PASS, structure/safety **31 PASS**, local Markdown
links/fragments **329 PASS**, `git diff --check` PASS. Все прежние Chromium cases:
**38/38**, без failed/skipped/cancelled. Новый opt-in probe: **2/2 PASS**, также
без skipped/cancelled; проверяет настоящий canvas и текущие server projections.

Последний baseline 30/200/15 (8 warm samples, nearest-rank p95):

| Измерение | Медиана | p95 |
| --- | ---: | ---: |
| Worker geometry/query CPU | 68.4 ms | 82.7 ms |
| Canvas paint/update на основном потоке | 39.5 ms | 42.7 ms |

Это не end-to-end latency, не время фактической GPU загрузки и не FPS/SLA.
В параллельных прогонах значения были выше. Heap основного JS context после GC
в этом опыте вырос с 10 265 704 до 14 759 168 bytes. Это **не доказательство
отсутствия утечек**: измерение включает JIT/Pixi caches, а worker heap/GPU memory
не измерены. Отдельно подтверждены единственный canvas/renderer, завершение
собственного worker, уничтожение своей Texture/source и обнуление canvas buffers
при dispose. Известное ограничение shader cache сохраняется.

Синхронизация visual metadata также проверена отдельно: сокрытие стены ручным
FoW должно отозвать visual observer даже при неизменных token IDs. Hub хранит
последние переданные metadata на соединение и сравнивает их **по содержимому**;
при изменении сервер отправляет существующий snapshot с тем же committed seq.
Запись удаляется при leave, не служит разрешением и не заменяет fresh stamp check.
