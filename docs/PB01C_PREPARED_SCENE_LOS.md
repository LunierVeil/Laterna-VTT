# PB-01c — подготовленная геометрия и внутренний LOS сцены

Статус: **реализация для независимого review, не одобрение интеграции света/FoW**.
База — `7c2d6b342242087eaf93657e2796f51d1de702a6` (PB-01b).
[Правила PB-01](PB01_VISIBILITY_RULES.md), [Beta-решения](BETA_DECISIONS.md),
[архитектура](ARCHITECTURE.md) сохраняют свои APPROVED/PROPOSED/OPEN-границы.

## Что подготовлено

[PreparedGeometry](../server/app/line_of_sight.py) принимает непрозрачные отрезки,
размеры сцены и стартовый epsilon. Один раз проверяет координаты, исключает точно
нулевые отрезки с подсчётом диагностики, сохраняет bounding boxes и точные
Fraction-координаты. Очень короткий ненулевой отрезок не удаляется.

Объект frozen/slots; коллекция отрезков — tuple, вложенные записи и координаты
неизменяемы. Внешние lists, генераторы или ORM-объекты не сохраняются по ссылке.
В repr объекта не включён список препятствий. Это удобство диагностики, **не
security boundary**: сам объект нельзя отправлять игрокам.

`geometry.point_sight(observer, target)` проверяет только две новые точки и
переиспользует подготовленные стены. Возвращает прежний `SightResult` с `CLEAR`,
`BLOCKED`, `OBSERVER_ON_OBSTACLE` и `ignored_zero_length`. Epsilon остаётся `1e-7 px`
как стартовое значение, не утверждённая окончательная точность. Диагностика считает
нулевые **непрозрачные входные** сегменты, а не все объекты сцены.

Существующий `point_sight()` PB-01b не переписан; PB-01a доступен через исходный
commit `cb45d31fd52daa1e9d83cd7e5bb261f4c4c5635d` и независимый test oracle.
Фильтры отсечения и точные предикаты переиспользуются без изменения epsilon.
Пространственный индекс, результатный кеш и новые зависимости не добавлены.

## Внутренний серверный API

Модуль [scene_sight.py](../server/app/scene_sight.py):

```python
from app.scene_sight import scene_sight, scene_sights

one = await scene_sight(scene_id, (100.0, 100.0), (600.0, 100.0))
batch = await scene_sights(scene_id, [
    ((100.0, 100.0), (600.0, 100.0)),
    ((100.0, 100.0), (300.0, 100.0)),
])
```

Это функции доверенного backend-кода, **не REST/WS endpoint**. Caller отвечает
за разрешённый контекст, выбранные точки и объём работы. `CLEAR` не отменяет
GM-only, ручной FoW или другие правила доступа. Диагностика, ID и геометрия
скрытых объектов игрокам не передаются: новых маршрутов/команд/рассылок нет.
Движение, snapshot, seq/cmd_id/base_seq, noop и reconnect не изменены.

Каждый вызов открывает новую `SessionLocal`, одним `SELECT Scene LEFT JOIN Wall`
читает только поля геометрии существующей сцены со всеми её стенами (без
повторной передачи fog_json/background на каждую joined-строку), копирует геометрию и закрывает
сессию. Лишь затем синхронно вычисляет результаты пачки. Пустая сцена имеет одну
строку с Wall=None; отсутствующая/удалённая сцена вызывает `SceneGeometryUnavailable`.
Даже пустая пачка не превращает неизвестную сцену в успешный ответ.

`prepare_scene_geometry(scene, walls)` — отдельный адаптер уже загруженных моделей.
Он **не проверяет актуальность** этих моделей: подходит для явно ограниченного
снимка/тестов, но не заменяет свежий серверный вызов. Смешивание стен разных сцен
отклоняется. Не сохранять его результат как глобальную «текущую сцену».

## Обычные стены, двери и неподдерживаемые данные

Используется разрешённое для PB-01c направление предложений P9:

| Данные | Непрозрачная геометрия |
| --- | --- |
| wall, blocks_sight=true | Включить |
| wall, blocks_sight=false | Исключить |
| door, open | Исключить независимо от blocks_sight |
| door, closed / locked | Включить независимо от blocks_sight |
| window / secret_door / invisible / неизвестный kind | Явная ошибка, не молчаливый CLEAR |
| door с неизвестным состоянием / wall с неоднозначным sight-флагом | Явная ошибка |

Вариант окон **W3 остаётся OPEN**, окончательные правила документа проходят
согласование. Стеклянные двери не вводятся. `blocks_movement`/`blocks_sound`
не подменяют `blocks_sight`. Никакие значения сохранений не преобразуются.

Невалидная непрозрачная геометрия (включая нечисловые координаты или выход за
текущие размеры) вызывает ValueError. В частности, Alpha позволяет уменьшить
сцену, оставив стену за новой границей: PB-01c **не обрезает** такую стену и не
переписывает БД, а отказывает в расчёте. Это ограничение для review; отдельное
правило clipping/редактора не выбирается молча. Повторное увеличение сцены может
сделать прежние координаты валидными снова.

## Актуальность и транзакции

Глобального кеша нет. Добавление/удаление стены, все состояния двери и resize
учитываются следующим вызовом, начавшимся после успешного commit. Транзакция с
flush без commit не публикуется в снимке другого подключения; rollback не меняет
следующий ответ. Никакие хуки handlers/main не инвалидируют состояние до commit.

Один SQL statement исключает смешивание размеров из одного чтения со стенами
из другого. Пачка — **point-in-time snapshot на момент SELECT**, не обещание, что
сцена останется неизменной до использования результата. Commit, конкурентный
самому чтению, может попасть в следующий снимок. Для будущего раскрытия объектов
понадобится отдельная серверная политика PB-02; этот результат не является lease.

Новый вызов не принимает старый PreparedGeometry/ORM session от caller. Старый
чистый объект остаётся историческим снимком и может возвращать старый результат;
его нельзя выдавать за актуальный. Тест проверяет, что такой объект не влияет
на новый серверный вызов. При выборе другой сцены передаётся её явный ID; active
scene не становится ключом общего кеша. После удаления следующий вызов — ошибка.

Новая сессия читает общую БД независимо от экземпляра приложения: сохранённый
результат другого процесса/запуска не переиспользуется. Тест использует отдельный
SQLAlchemy engine для изменения двери. Это **не исправление** существующей
координации WS-команд между несколькими workers: Hub.lock остаётся локальным
процессу. Разные независимые БД автоматически не синхронизируются.

## Проверки и воспроизведение

```bash
server/.venv/bin/python -m pytest server/tests/test_los_geometry.py server/tests/test_los_broadphase.py server/tests/test_los_prepared.py server/tests/test_scene_sight.py server/tests/test_pb00_baseline.py -q
server/.venv/bin/python scripts/benchmark_prepared_los.py --samples 5
```

[Unit tests](../server/tests/test_los_prepared.py): копирование mutable-входа,
frozen-структуры, отсутствие повторной валидации/Fraction-конвертации стен,
ε/углы/нулевые и короткие сегменты, 200/2000/10000 стен, независимый exact oracle.
[Integration tests](../server/tests/test_scene_sight.py): реальные WS-команды,
двери с обоими flags, rollback, отдельный engine, смена/удаление сцен, resize,
старый snapshot, ровно один SELECT на 100 запросов, неподдерживаемые старые данные.
PB-00 сохраняет существующие проверки privacy/REST/snapshot/noop/reconnect;
его characterization публичного /uploads остаётся GAP для PB-02.

Benchmark извлекает PB-01a и PB-01b из закреплённых Git commits. Нужна локальная
история этих commits. Результаты сравниваются до измерения. Измеряется **чистая
геометрия**, без SQL, ORM-загрузки, HTTP и network latency. Подготовка из реальных
моделей и свежесть чтения проверены интеграционными тестами; это не замер DB SLA.

Подготовка и один повторный запрос измеряются для 200/2000/10000 стен. Пачки
100/1000/10000 лучей измеряются на **24 базовых стенах**, не на 10000 стенах.
Это разные оси нагрузки. В профиле door_changes к 24 стенам добавляется одна
закрытая дверь; перед каждым новым запросом геометрия пересоздаётся. Поэтому
его время включает refresh + query; остальные пачки используют один снимок,
стоимость подготовки показана отдельно.

На каждую операцию — один прогрев и пять измерений; p95 nearest-rank при пяти
samples равен максимуму, это грубая диагностика, не надёжная оценка хвоста SLA.
Для более устойчивой статистики можно увеличить `--samples`, не меняя dataset.
Замеры не запускать параллельно с pytest/build/другим benchmark. Timing gates нет.

### Выводы и ограничения

- Повторное использование уменьшает валидацию и конвертацию, но не устраняет
  точный Fraction fallback. Близкие препятствия по-прежнему дороги.
- Полная подготовка заранее конвертирует даже далёкие стены. Для одного запроса
  она может быть хуже ленивого PB-01b; окупаемость зависит от числа лучей/геометрии.
- **При смене двери перед каждым лучом новый подход медленнее:** подготовка не
  амортизируется. Это цена выбранного простого snapshot-подхода; глобальный кеш
  или сложная инвалидизация ради цифр не добавляются. Пачки следует ограничивать
  одной явно выбранной версией геометрии, не переиспользовать через изменения.
- Запросы пачки выполняются синхронно; большие пачки в event loop могут задерживать
  другие задачи. В рабочие сетевые обработчики они не подключены. Перед таким
  подключением нужны согласованные лимиты/планирование/нагрузочные испытания.
- SQL/ORM/read-session latency не включена в таблицу. Один свежий SELECT на пачку
  проверен тестом, но его стоимость зависит от БД и числа стен.
- Нет разрешения массового LOS, освещения, FoW, personal/shared vision или нового
  ACL. W3 остаётся OPEN; неподдерживаемая/вышедшая за границы геометрия — явная
  ошибка, не CLEAR. Подключение выдачи защищённых объектов — отдельный PB-02.
- Схема/сериализация/движение не изменены. Окончательная оптика P9 и поведение
  после уменьшения сцены до границы старых стен требуют review владельца.
