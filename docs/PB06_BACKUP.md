# PB-06 A — ядро проверяемого backup

[Issue #47](https://github.com/LunierVeil/Laterna-VTT/issues/47) задаёт
приёмку всего PB-06. A вводит внутренний online API и read-only verify.
B реализует restore в новый DataHome. C подключает ручные команды, Windows
launcher и проверку извлечённого ZIP. Расписание и политики хранения вне A.

## Согласованность при работающем сервере

SQLAlchemy открывает существующую файловую SQLite в режиме `rw`. Laterna
не принуждает SQLite к WAL. Штатные startup-проверки PB-05 применяются
перед запуском сервера, но не повторяются поверх живого подключения.
Backup открывает отдельное read-only SQLite-соединение, без `immutable`
для исходной БД, и создаёт снимок через Online Backup API. В staging
SQLite приводится к автономному rollback journal mode. Джорналы исходной
БД не копируются и не удаляются. Пользовательская схема не меняется.

Единственный файловый write path uploads — POST. Он публикует целиком
записанный файл атомарной заменой временного имени. URL выдаётся после
публикации, перезапись опубликованных файлов и удаление uploads приложением
не поддерживаются. Обновления ссылок и удаления игровых объектов меняют
SQLite, кэш preview находится отдельно. Сначала создаётся снимок SQLite,
потом собираются завершённые uploads. Файлы, добавленные после снимка,
могут попасть в копию как несвязанные. Проверка охватывает ссылки на
uploads из сцен, токенов и вложений в данных персонажей. Если подходящая
ссылка не найдена в копии, публикация отменяется. Внешнее редактирование
файлов не поддерживается, изменения во время чтения проверяются по
метаданным дескриптора и пути. Временные файлы загрузки недоступны через
media и исключаются из bundle.

`app.state.instance_backup.create(destination)` выполняет работу в потоке,
под OS locks уже запущенного экземпляра. Вторая операция сразу отклоняется.
Lifespan дожидается завершения backup перед освобождением locks, даже если
инициатор перестал ждать. Глобальной блокировки HTTP/WS-записей нет.
Кооперативный лимит по умолчанию 120 секунд проверяется между порциями
данных, шагами SQLite и перед публикацией. Он не прерывает зависший
системный вызов. Лимиты формата A — 10 000 файлов uploads, 64 GiB payload,
4 MiB manifest. Это технические границы PR для review, не утверждённые
параметры G3 или RTO. PostgreSQL и in-memory DB не поддерживаются.

## Формат каталога v1

`manifest.json`, `lanterna.db`, `uploads/` и, при файловом ключе, `gm_key.txt`.
Manifest содержит UTC, source commit при наличии в пакете, `user_version`
SQLite, режим ключа, размеры, SHA-256 и статус завершения и проверки. При
`key_mode=external` значение и отпечаток `LANTERNA_GM_KEY` не сохраняются.
Для будущего восстановления оператору нужен исходный внешний секрет.
Каталог с файловым ключом содержит чувствительные данные, храните его как
оригинальный DataHome. SHA-256 обнаруживает повреждение, подлинность не проверяет.

Read-only `verify_backup` сравнивает полный состав, размеры, SHA-256,
проверяет SQLite integrity/FK, ссылки на изображения и ключ. Успех также
подтверждает совместимость с политикой запуска PB-08B. Принимаются точный
каталог Alpha или текущий каталог с единственной ревизией
`0001_alpha_baseline`, нулевые `application_id` и `user_version` и кампания
с активной сценой. Неизвестная ревизия и drift приводят к отказу даже при
валидном manifest и успешной проверке целостности. Формат manifest v1
сохраняется, каталог проверяется по фактической SQLite. Проверка открывает
копию только для чтения. Staging находится в приватном временном
каталоге на целевом томе. Публикация использует rename без перезаписи
`renameat2(RENAME_NOREPLACE)` на Linux и `os.rename` на Windows. ФС без такой
гарантии отклоняются. После обычного отказа удаляется только свой staging.
После принудительного завершения скрытый staging может остаться, он никогда
не является опубликованной копией. Атомарность имени не является гарантией
сохранности при отключении питания.

Restore, запуск восстановленной копии, управление внешним секретом через
пользовательский интерфейс и Windows package smoke относятся к следующим PR.

## Этап B — проверяемое восстановление

Внутренний `app.instance_restore.restore_backup(backup_path, destination_data_home,
schema, external_gm_key=...)` принимает абсолютные пути. Назначение должно
отсутствовать, включая случай заранее созданного пустого каталога. Родитель
назначения должен существовать, быть доступным для записи и контролироваться
оператором. Restore не поддерживает архивную распаковку или замену работающего стола.

Перед записью Restore применяет тот же контракт `verify_backup` к исходному
комплекту. Для назначения захватываются
штатные PB-05 locks на SQLite, uploads и путь ключа. Они остаются удержанными до
публикации и очистки. Приватный staging на целевом томе получает файлы с повторным
сравнением размеров и хешей. Затем весь комплект независимо проходит
`verify_backup` и startup preflight. Публикация выполняется атомарным rename без
замены. Manifest остаётся у исходного backup и возвращается вызывающему коду.
В DataHome публикуются SQLite, uploads и файловый ключ, если он был в backup.

Для `key_mode=external` нужен исходный `LANTERNA_GM_KEY` при восстановлении
и при последующем запуске. Значение не сохраняется, проверить его подлинность
по manifest нельзя. Для файлового ключа при запуске используйте восстановленный
файл без переопределения через env. Restore не создаёт ключи и не запускает DDL.

| Отказ | Результат |
| --- | --- |
| Повреждение, несовместимая схема, пропуск файла, небезопасное имя | Отказ до создания staging |
| Изменение payload после проверки | Сравнение с первоначальным manifest останавливает копирование |
| Занятый или существующий DataHome | Отказ OS lock либо атомарной публикации без замены |
| ENOSPC, EACCES, EIO | Итоговый DataHome не появляется. Удаляется только принадлежащий операции staging |
| Остановка процесса | Скрытый staging может остаться. Итоговое имя отсутствует до публикации |
| Подмена родителя или staging | Отказ, обнаруженный чужой каталог не очищается |
| Отсутствующий внешний ключ | Отказ до копирования. Backend также отклоняет запуск без ключа |

Гарантии рассчитаны на доверенный локальный каталог назначения и процессы,
соблюдающие PB-05 locks. Проверка путей и их идентичности не делает произвольную
локальную файловую систему безопасной при активном вмешательстве пользователя
с правом переименовывать родительские каталоги. Windows ZIP, CLI и конечная
приёмка относятся к C.

## Ручные команды

1. Запустите стол обычным способом. На Windows откройте **Резервные копии** во втором окне `laterna.bat` с тем же Profile или Portable. Выберите **Создать копию работающего стола**. На Linux во втором терминале запустите `./laterna.sh backup create` с тем же DataHome.
2. Дождитесь `Verification: PASSED`. Команда показывает фактический путь копии. Стол выбирает уникальное имя в каталоге **Laterna Backups** рядом с DataHome. Скопируйте весь опубликованный каталог на другой носитель, чтобы отказ одного диска не уничтожил оригинал и копию.
3. Для независимой проверки используйте **Проверить копию** или `./laterna.sh backup verify "/absolute/path/to/copy"`.
4. Для восстановления выберите **Восстановить в новый DataHome** или `./laterna.sh backup restore "/absolute/path/to/copy" "/absolute/path/to/new home"`. Укажите новое имя в существующем каталоге, доступном для записи. После работы сохраните исходную копию и прежний стол.
5. Откройте результат явным запуском. На Windows используйте `laterna.bat -RestoredDataHome "C:\\path\\to\\new home"`. Это не переключает Profile или Portable. На Linux задайте `LANTERNA_REQUIRE_EXISTING=1 LANTERNA_DATA_HOME="/absolute/path/to/new home" ./laterna.sh`. При backup с внешним ключом исходный `LANTERNA_GM_KEY` должен быть установлен в окружении при восстановлении и запуске. Передавать ключ в аргументах команд не требуется.

Windows также поддерживает `-Action Backup`, `-Action Verify -BackupPath ...`
и `-Action Restore -BackupPath ... -Destination ...`. Для первого окна
с установленным Profile или Portable используйте сохранённый выбор или явно
задайте тот же `-Storage` при работе с копией.

Ошибка возвращает ненулевой код. При отсутствии ответа убедитесь, что запущен
именно нужный стол. Если запрос уже был принят, проверьте каталог копий и
запустите Verify. Принудительная остановка может оставить скрытый staging
или старую папку сеанса управления. Новый сервер игнорирует запросы прежнего
сеанса. Работающую SQLite копируйте через Laterna: обычная копия файла может
пропустить WAL и разойтись с uploads.

### Локальная граница доступа

Команда создания использует локальную файловую очередь в
`.backup-control` выбранного DataHome (для Linux development — рядом
с SQLite). В очередь передаётся пустой запрос со случайным идентификатором.
Случайный сеанс создаётся заново при каждом запуске владельца PB-05.
Сервер выбирает назначение, проверяет каталог назначения и выполняет
имеющийся `OnlineBackup` под блокировками. У HTTP и WebSocket нет
операций backup, restore или выдачи полной копии. CLI не передаёт секреты.

На Linux каталог канала ограничен текущим владельцем. На Windows доступ
наследуется от DataHome. Используйте профиль пользователя или приватный
каталог для Portable. Пользователь ОС, у которого есть запись в DataHome,
уже находится внутри границы доверия. Используйте доверенный родительский
каталог и для **Laterna Backups**. Online create поддерживает файловую SQLite
в едином DataHome и Linux development по умолчанию. При отдельных overrides
он недоступен. Verify и restore выполняются без игрового сервера.

[Автоматическое расписание и retention](PB07_AUTOMATIC_BACKUP.md) относятся к
PB-07 B. Обязательный pre-upgrade snapshot описан в [контракте PB-07 C](PB07_AUTOMATIC_BACKUP.md#pb-07-c--предобновительный-gate).
