# PB-21A — контракт редактора NPC

PB-21A задаёт типы и независимую копию данных редактора для D&D 5e 2014. PB-21B проектирует подключение листа, хранение и UX. Критерии полного PB-21 перечислены отдельно в [Issue #62](https://github.com/LunierVeil/Laterna-VTT/issues/62) и [roadmap](ROADMAP.md#полноценный-редактор-npcмонстров--must-beta-c). Применяются [LTR-DEC-006–008](BETA_DECISIONS.md#восемь-продуктовых-решений--approved) и серверная модель доступа к листам.

## Что уже работает

| --- | --- |

Отдельных действий сверх таблицы атак, бонусных, легендарных, логовищных действий и заклинаний в mob нет. |

## Контракт редактора

`NpcDraftContent` содержит имя, редакцию `2014`, `NpcStatblock`, необязательное происхождение SRD 5.1 и необязательный снимок исходного legacy JSON. `NpcDraft` добавляет выданный вызывающей стороной `sheetId`. Модуль находится в модели `systems/dnd5e` и доступен для будущей композиции приложения. Типы описывают данные редактора in-memory. У них пока нет схемы сохранения, декодера пользовательского JSON или привязки к `Character.data`. [Контракт](../web/src/systems/dnd5e/model/npc-contract.ts)

Базовые поля допускают неполные ручные заготовки. AC и максимум HP могут сопровождаться условиями и формулой hit dice. Шесть характеристик используют знакомые ключи `str`–`cha`, с напечатанным или ручным модификатором при наличии. Спасброски и навыки раздельные, CR — текст с дробями, XP — отдельное число. Движение, защиты, иммунитеты к состояниям, чувства и языки могут содержать условия. `conditionNotes` хранит правила о состояниях существа, а активные состояния принадлежат экземпляру в столкновении.

`sections` хранит упорядоченные Traits, Actions, Bonus Actions, Reactions, Legendary Actions и Lair Actions. Элемент имеет стабильный ID, заголовок и полный текст. Теги `multiattack`, `spellcasting`, `innateSpellcasting` позволяют находить карточки в исходной секции. Опциональные поля атаки описывают ввод для ручной работы. Прологи legendary/lair хранятся отдельно. Метки recharge, лимиты применений, ручные инструкции и ссылки на счётчики дополняют текст. У счётчика есть ID, имя, максимум, текущее значение в черновике и необязательное текстовое условие восстановления. Кто хранит состояние расхода в игре, решает интеграция. Парсер боевых правил, автоматические расходы, применение состояний и восстановление в этот этап не входят.

`copyNpcDraft(content, sheetId)` делает глубокую копию JSON-совместимых данных без генерации ID. Исходное оборудование, RichText, расширения, provenance и полный текст сохраняются. TypeScript `readonly` ограничивает изменение через интерфейс. На runtime вложенные значения остаются обычным JSON.

### Совместимость legacy mob

Действующие `mob`, `dnd5e`, `SheetSchema`, редакторы и поля DTO используются как прежде. `legacyMobData` может нести оригинальный JSON листа целиком, включая оборудование, `portrait`, `initiative`, `notes` и любые вложенные ключи RichText. Это снимок для сохранения данных. Для каждого сохранённого редактируемого NPC нужен один канонический источник истины. Legacy JSON, provenance и снимок каталога служат сохранению исходных данных, а отображения строятся из канонической записи. Какую форму хранить и как подключить старый редактор, определит PB-21B. Преобразование полного NPC обратно в старый mob было бы частичным. Ограничения перечислены ниже и требуют явного поведения в будущем адаптере.

### Преобразование полей

Для `SavingThrow.name` используется точное сопоставление литералов: `Str → str`, `Dex → dex`, `Con → con`, `Int → int`, `Wis → wis`, `Cha → cha`. Результат записывается в `savingThrows[].ability`, `bonus` и порядок сохраняются. Сопоставление не зависит от локали. Значение вне этих шести литералов означает несовпадение контрактов.

`None` в необязательном поле каталога означает отсутствие соответствующего ключа в черновике, например `armor_class_details: None` оставляет только `armorClass.value`. Проверка наличия опирается на `None`, поэтому валидные `xp: 0`, `armor_class: 0` и `modifier: 0` переносятся как числа. Та же логика применяется к `HomebrewDraft.origin: None`, при котором `NpcSrd51Provenance` отсутствует. Эти правила касаются переноса из каталога. В исходном `legacyMobData` сохраняются и присутствующие `null`, и отсутствующие ключи.

### Идентичность, исходник и владение данными

- `srd51:<slug>` идентифицирует запись каталога. Вызывающий код выдаёт `HomebrewDraft.id` при создании независимого снимка. Повтор того же импорта использует уже выданный ID, новый независимый импорт получает свой. `sheetId` отдельно идентифицирует лист, а `Token.id` — экземпляр с ссылкой `character_id`. Копия листа получает новый `sheetId`, наследует происхождение и владеет глубокой копией содержимого.
- PB-20A передаёт способности как упорядоченные `label/text` без ID. Будущий адаптер назначает ID один раз при первой материализации листа и сохраняет их вместе с карточками. ID уникальны внутри листа и переживают повторное чтение, повтор операции, редактирование текста и перестановку. Заголовок, индекс и текущий порядок каталога не используются как постоянный ID. При копировании листа локальные ID можно сохранить вместе со ссылками внутри копии, поскольку меняется `sheetId`.
- Для provenance из `HomebrewDraft.origin` берутся `template_id`, `source`, диапазон страниц, последняя строка и SHA-256 документа. `title`, `language`, `document_url`, `license`, `license_url`, `attribution` и `changes` берутся из `SrdCatalog.manifest` той же проверенной редакции каталога. При создании копии сверяются `origin.source == manifest.id` и `origin.document_sha256 == manifest.document_sha256` и сохраняются значения manifest. Для загруженной позднее копии применяется её зафиксированный manifest. Отсутствие или расхождение этих данных требует явной ошибки будущего адаптера.
- При первом переносе `label`, `text`, прологи и `source_note` сохраняются целиком вместе с порядком, условиями и разрывами строк. Теги и вспомогательные поля дополняют исходный текст. Правки листа и обновления каталога не меняют другие снимки или их provenance. Хранилище должно предоставлять один канонический редактируемый источник данных на NPC. Каталог, снимок происхождения, legacy JSON и проекции не должны порождать вторую независимо редактируемую запись.

PB-20A и PB-21A согласовали перенос полей и владение данными. Будущая структура импорта в памяти сохраняет `manifest.catalog_schema_version` отдельно от `NpcSrd51Provenance`: SHA-256 идентифицирует PDF. Место, где хранить версию каталога после сохранения NPC, остаётся открытым для PB-20B/PB-21B.

## Инвариант HP

| Событие | Поведение |
| --- | --- |
| Создан токен mob или токен привязан к другому листу mob | Действующий сервер инициализирует `Token.hp` из максимума нового шаблона. Повторная привязка к тому же листу сохраняет текущее значение |
| Лист переименован, изменились способности, ресурсы или оборудование | Текущие HP 2, 5 и 7 у трёх экземпляров остаются в соответствующих токенах. `hp.max` остаётся полем листа, в черновике это `statblock.hp.max` |
| Изменился `hp.max` | Сейчас редактируется лист, максимум из его проекции меняется, `Token.hp` существующих экземпляров напрямую не записывается. Новый экземпляр инициализируется новым максимумом. Будущая политика при превышении текущих HP над новым максимумом, временных максимумах и давлении на UI — отдельное решение PB-21B |
| Показ данных игроку | Действующие границы доступа к листу и проекции токена сохраняются. Синтетический draft никуда не публикуется |

### Открытые решения PB-21B

| Вопрос | Что согласовать перед интеграцией |
| --- | --- |
| Ресурсы | Какие счётчики принадлежат листу, какие экземпляру токена и какие значения получает новый экземпляр. |
| Runtime validation | Границу проверки входных данных, обязательность полей, числовые пределы, уникальность ID и ссылки между карточками и ресурсами. Строгие проверки SRD относятся к входу каталога. Ручные NPC допускают собственные характеристики, CR, XP и способности в пределах технических ограничений. |
| Schema version | Форму единственного канонического хранилища, версию схемы и совместимость старых записей и копий. |
| Уменьшение максимума HP | Как показывать и обрабатывать текущие HP выше нового максимума, сохраняя раздельные `hp.max` и `Token.hp`. |
| ACL и ownership | Кто создаёт, редактирует, копирует и читает лист, provenance, legacy JSON и данные экземпляра, включая отзыв прав. |
| Lossless legacy round trip | Какие поля читают оба редактора, как сохранять неизвестные ключи, RichText и снаряжение при загрузке, редактировании и повторном сохранении. |
| Совместимость с PB-20B | Границу выдачи UUID, фиксации manifest, копирования и сохранения. Импорт и редактор должны использовать одну каноническую запись NPC с согласованным жизненным циклом. |
