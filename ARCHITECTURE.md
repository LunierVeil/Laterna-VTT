# Laterna VTT - архитектура

Открытый self-hosted VTT. Laterna VTT - финальное название (лат. "фонарь").

Во внутренних именах осталось старое написание `lanterna`: cookie
`lanterna_session`, ключи `localStorage` (`lanterna.*`), `LANTERNA_GM_KEY`,
имя файла базы, пользователь Postgres в compose, папка. Их смена разлогинила
бы всех и сломала настроенные окружения ради буквы, которую видит только код.

## Зачем этот проект

Бесплатный VTT, который мастер поднимает у себя. Цель - закрыть то,
за что приходится платить или терпеть в других:
- Roll20: свет и стены работают только по подписке, неудобный интерфейс
- Foundry: $50 разово, но главный барьер - хостинг у мастера
- Owlbear Rodeo: бесплатный и простой, свет есть через официальное
  расширение. Главный конкурент. Отличаться от него: открытый код и
  свой сервер, русский язык, импорт персонажей из LSS, Режиссёр событий
Перед новой большой фичей спросить: решает ли она одну из этих проблем.
## Принципы

1. **Сервер - источник правды.** Клиент не меняет состояние сам, он шлёт команду. Сервер валидирует, применяет, рассылает событие. Клиент применяет событие.
2. **Клиент может применить оптимистично**, но помечает изменение как неподтверждённое и откатывает, если сервер прислал другое.
3. **Геометрия и рендер - на клиенте.** Python ничего не рисует и не считает полигоны видимости. Его работа: auth, хранение, валидация, рассылка, броски кубов.
4. **Стены существуют с первого дня**, даже пока свет не реализован. Переделывать схему сцены потом дороже, чем заложить поля сейчас.
5. **Никакой системы правил в ядре.** Лист персонажа - это JSON + схема полей. Хардкод одной системы появится позже, модульность - ещё позже, и только после того, как одна система заработает.

## Модель данных

```
Campaign           active_scene_id
  User             имя, argon2-хеш пароля, is_gm
    AuthSession    sha256 токена сессии
  Scene            грид, фон, размеры, бой (трекер инициативы)
    Layer          background | tokens | walls | gm
      Token        x, y, размер в клетках, картинка, owner_id, character_id, vision_range
      Wall         x1,y1,x2,y2 + флаги, owner_id
  Message          чат и броски, author + author_id
  Character        owner_id, name, system, data (JSON по схеме), исходник импорта
```

Владелец - **id пользователя, не имя**: имя можно сменить, а совпадение
имён ничего не должно значить.

### Wall - поля с первого дня

| поле | зачем |
|---|---|
| `blocks_movement` | токен не проходит |
| `blocks_sight` | перекрывает видимость (пока не используется) |
| `blocks_sound` | на будущее |
| `kind` | `wall` / `door` / `secret_door` / `window` / `invisible` |
| `door_state` | `closed` / `open` / `locked` |
| `owner_id` | кто поставил (id); удалить может он или ГМ. `null` - общая стена |

Сегодня работают `blocks_movement` и двери (`kind = door`, `door_state`).
Остальное лежит в БД и ждёт этапа освещения.

### Двери

Закрытая и запертая дверь блокирует движение, открытая - нет (это
проверяет сервер, как и стены). Открыть и закрыть дверь может любой - в
игре персонажи открывают двери сами. Запереть и отпереть - только ГМ:
иначе игрок отпирал бы запертое кликом. Команда `wall.door`, событие
`wall.updated`.

Сервер пока принимает только `wall` и `door`. Тайная дверь, окно и
невидимая стена есть в модели, но **тайную дверь нельзя слать игроку как
тайную** - это утечка, как со скрытыми сценами и токенами. Её надо
маскировать под обычную стену на сервере; это сделаем вместе со светом.

Зона клика токена - ровно его круг (`hitArea`). Без этого PixiJS ловит и
обводки: кольцо выделения дотягивалось до соседней клетки, и клик по
двери рядом с выбранным токеном доставался токену.

### Координаты

Всё хранится в **пикселях сцены**, а не в клетках. Сетка - это способ отображения и привязки, а не единица хранения. Иначе гексы и бессеточные карты потом не вставить.

### Расстояния

Линейка и подпись при перетаскивании токена считают клетки как в 5e по
умолчанию: диагональ - тоже одна клетка, клетка - 5 футов (пока
константа на клиенте; станет настройкой сцены, когда понадобится другой
масштаб). При перетаскивании привязанного к листу токена видно "25 / 30
фт" - скорость из листа. **Ход дальше скорости не запрещается** - это
подсказка, а не правило: рывок, хоумбрю и ошибки в листе решает стол.
Сервер при движении проверяет только стены.

## Протокол

Один websocket на сцену: `/ws/scene/{scene_id}`. Кто подключился, сервер
берёт из cookie сессии - в адресе о пользователе ничего нет. Без сессии
приходит `{ "type": "auth_required" }` и сокет закрывается (4401).

**Клиент -> сервер (команда):**
```json
{ "type": "cmd", "id": "uuid-клиента", "name": "token.move", "payload": {...} }
```

**Сервер -> клиент (событие):**
```json
{ "type": "event", "seq": 42, "name": "token.moved", "payload": {...}, "cmd_id": "uuid-клиента|null" }
```

**При подключении:**
```json
{ "type": "snapshot", "seq": 42, "scene": {...}, "you": { "id": "...", "name": "...", "is_gm": false } }
```

**Мимо seq сцены** (общее на кампанию, получают все подключённые):
```json
{ "type": "chat", "message": {...} }
{ "type": "campaign", "active_scene_id": "...", "scenes": [...], "users": [{ "id": "...", "name": "...", "is_gm": false }] }
{ "type": "reply", "name": "scene.created", "payload": {...}, "cmd_id": "..." }
```
`scenes` в `campaign` приходит только ГМ, `users` - всем (имена и так
видны в чате; клиенту они нужны, чтобы подписать, чей токен). `reply` -
ответ одному отправителю команды кампании.

`seq` - монотонный счётчик на сцену. Клиент хранит последний применённый seq. Если пришло событие с seq <= текущего, игнорирует (повтор). Если разрыв - перезапрашивает снапшот. Это дешёвая замена полноценному event sourcing и её хватит надолго.

`cmd_id` возвращается, чтобы клиент понял, какое из его оптимистичных изменений подтвердилось.

### Числа в командах и ошибки хендлеров

`json.loads` и pydantic принимают `Infinity` и `NaN`, а `1e400` даёт
бесконечность. Такое число в координатах стены сохранялось, и снапшот
сцены падал с 500 у всех - стол ломался одной командой. Поэтому числа из
команд - только через `_as_num`/`_num`/`_int` в handlers.py: не число или
не конечное - `CommandError`. Стены зажимаются в границы сцены, как токены.

Хендлер упал не `CommandError`, а исключением - клиенту «внутренняя
ошибка», в лог traceback, а сокет живёт дальше. Раньше исключение
пробрасывалось, выходило из цикла приёма и рвало соединение игроку.

### Команды

Сцены (событие с seq, рассылается в комнату сцены):

| команда | событие | кто |
|---|---|---|
| `token.add` | `token.added` | все |
| `token.move` | `token.moved` | владелец или ГМ |
| `token.update` | `token.updated` | владелец или ГМ; `layer` - только ГМ |
| `token.remove` | `token.removed` | владелец или ГМ |
| `wall.add` | `wall.added` | ГМ |
| `wall.remove` | `wall.removed` | владелец или ГМ |
| `wall.door` | `wall.updated` | открыть/закрыть - все; запереть/отпереть - ГМ |
| `scene.update` | `scene.updated` | ГМ |
| `combat.add` | `combat.updated` | свой токен; ГМ - любой |
| `combat.set`, `combat.roll`, `combat.remove` | `combat.updated` | своя строка; ГМ - любая |
| `combat.next` | `combat.updated` | ГМ; игрок - только закончить свой ход |
| `combat.end` | `combat.updated` | ГМ |

Кампании (без seq, `handle_campaign` в main.py):

| команда | что уходит | кто |
|---|---|---|
| `chat.say` | `chat` всем | все |
| `dice.roll` | `chat` всем - бросок с подписью из листа | все; `hidden` - ГМ |
| `scene.create` | `reply` + `campaign` | ГМ |
| `scene.activate` | `campaign`, игроки переезжают | ГМ |
| `scene.delete` | `campaign` | ГМ, не активную |
| `invite.create` | `reply` с кодом (только ему) + `campaign` | ГМ |
| `invite.revoke` | `campaign` | ГМ |
| `player.delete` | `campaign`, сокеты игрока закрываются | ГМ, не себя |
| `character.create` | `reply` + `character` владельцу и ГМ | все (себе), ГМ - кому угодно |
| `character.update` | `character` владельцу и ГМ | владелец или ГМ |
| `character.delete` | `character_deleted` владельцу и ГМ | владелец или ГМ |

### Скрытые токены (слой ГМ)

Токен со слоем `gm` - засада, ловушка, NPC, которого игроки ещё не
видят. **Игроку он не уходит вовсе**: ни в снапшоте (сокет и REST), ни в
событиях, ни строкой в трекере боя. Ставить токены скрытыми и
показывать их может только ГМ.

- seq сцены у всех один. Если просто не отправить игроку событие про
  скрытый токен, клиент увидит разрыв нумерации и перезапросит снапшот.
  Поэтому игрок получает пустое событие `noop` с тем же seq: порядок цел,
  содержимого нет.
- Показали токен - игрок получает `token.added` (появился), спрятали -
  `token.removed` (исчез), а не исходный `token.updated`.
- Хендлер помечает событие (`_with_hidden`: скрыт ли токен до и после),
  `main.event_for` строит его для каждого получателя.
- Строка скрытого токена в бою игроку не видна (засада в трекере выдала
  бы засаду). Если засаду показать посреди боя, её строка появится у
  игроков со следующим изменением боя.

### Мобы и NPC

Моб - лист с `system = "mob"`: имя, портрет, хиты (максимум), КД,
скорость, атаки, заметки. Заводит и видит только ГМ - как любой его лист.

**Лист моба - шаблон, а не существо.** «На карту» ставит экземпляр:
сервер даёт ему номер («Гоблин 1», «Гоблин 2»), полные хиты и портрет
из листа. Текущие хиты экземпляра - на токене (`Token.hp`), иначе пять
гоблинов с одного листа падали бы от одного удара. Максимум, КД и атаки
берутся из листа: поправил шаблон - поменялось у всех экземпляров.

Нужен другой вариант («гоблин с луком») - `character.copy`, копия листа,
а не правка шаблона. Так же потом встанет бестиарий: готовый моб, из
которого ГМ делает свою копию.

**Токен персонажа игрока ставится так же** - «На карту» в списке листов
шлёт тот же `token.add` с `character_id`, а не отдельную команду.
Отличия от моба: имени с номером нет, хиты не копируются (они в листе),
владельцем токена становится владелец листа, даже если ставил ГМ - иначе
игрок не смог бы ходить своим персонажем. Кнопку видит ГМ и владелец
листа. Если токен этого листа уже на сцене, кнопка выделяет и центрирует
его (Shift - поставить второй); токены слоя ГМ игроку не приходят, так
что у него кнопка поставит новый - это нормально. Слой при постановке не
шлётся: токен персонажа видимый, спрятать его мастер может в настройках.

- `Token.hp` игрокам не уходит, кроме владельца токена
  (`main.token_for` - в событиях и снапшоте). Хиты моба выдали бы,
  сколько осталось добить.
- `hp` в `token.add` не принимается - только из листа. В `token.update`
  - только если токен привязан к мобу; хиты персонажа игрока живут в
  его листе, второй источник правды им не нужен.
- Портрет - строка в данных листа, а их сервер проверяет только по
  форме. Поэтому на токен портрет попадает через `_upload_url`, а клиент
  рисует только адрес вида `/uploads/...` (`safeUpload`).
- Новая колонка, которая может быть NULL, добавляется в старую базу при
  запуске (`db._check_columns`). Остальные изменения схемы - всё ещё
  пересоздание базы, пока нет alembic.

### Ручной туман и пинг

**Туман** - прямоугольники в пикселях сцены (`Scene.fog_json`, `fog.py`),
меняет только ГМ: `fog.cover`, `fog.reveal` (вычитает прямоугольник,
старые распадаются на остатки), `fog.cover_all`, `fog.clear`, `fog.undo`.
Под туманом игроку не уходят токены (кроме своих - свой персонаж в
закрытой комнате не пропадает) и стены целиком под ним - тот же механизм,
что у слоя ГМ: пометка в хендлере, `event_for` решает для получателя
(событие, `noop`, «появился», «исчез»). На смену тумана игрок получает
`fog.updated` со списками того, что у него появилось и исчезло.
- Отмена - только своего последнего шага (история в памяти процесса); если
  последним менял другой мастер - отказ.
- Честно: карта-картинка уходит игроку целиком, туман над ней - только
  рисунок; от токенов туман не открывается; памяти разведанного нет.
  Строка токена в трекере боя под туманом пока видна (только имя).

**Пинг** - не состояние сцены: без seq, без базы, при переподключении не
повторяется. Сервер проверяет числа, режет чаще 700 мс на пользователя и
рассылает всем в сцене сообщение `ping`.

### Бой (трекер инициативы)

Состояние боя - в сцене (`combat_json`): участники, чей ход, раунд.
Меняется только командами `combat.*`, рассылается всем в сцене событием
`combat.updated` с полным состоянием - оно маленькое.

- **Чей ход - id участника, а не номер в списке.** Добавили участника или
  поменяли инициативу посреди раунда - ход не перескакивает на другого.
  Порядок - по убыванию инициативы, считает сервер.
- **Бросок инициативы - на сервере** (`1d20` + бонус). Клиент шлёт только
  бонус, взятый из листа (путь - в схеме, `token.initiative`); в строке
  видно, что выпало на d20, - бросок честный, а не вписанный.
- Имя, владелец и лист участника сервер освежает с токена при каждом
  изменении: панели нужно знать, кому показывать кнопки, а токены в React
  не живут. Это id, не данные листа.
- Чей ход - видно и на карте: кольцо вокруг токена.

### Сцены и что видят игроки

Игрок видит только активную сцену кампании (`active_scene_id`), ГМ -
любую. Остальные сцены - заготовки, и **сервер их игроку не отдаёт
вообще**: ни сокет, ни REST-снапшот, ни список. Прятать на клиенте
нельзя - всё, что пришло в браузер, видно в DevTools.

Когда ГМ показывает другую сцену, сервер шлёт игрокам `campaign` и сам
закрывает их сокеты в старой сцене. Клиент по `campaign` переподключается
в новую. Полагаться на то, что клиент уйдёт сам, нельзя.

Чат общий на кампанию, а не на сцену: ГМ в заготовке видит игроков, а
смена сцены не стирает историю бросков. Поэтому он идёт мимо seq сцены -
иначе сообщение из чужой сцены выглядело бы для клиента разрывом нумерации.

### Броски кубов - только на сервере

Клиент шлёт строку `2d6+3`. Сервер парсит, бросает, рассылает результат вместе с отдельными кубами. Клиент никогда не генерирует случайное число для броска. Иначе любой игрок с девтулзами крутит d20 как хочет.

**Скрытый бросок мастера** (`/gr 1d20`, галочка "скрыто" в панели кубов -
она же действует на броски из листа): результат видит только ГМ. Игроку
сервер шлёт заглушку `hidden_roll` - кто бросил, и всё: ни формулы, ни
подписи, ни кубов, ни итога - ни вживую, ни в истории чата при входе.
Признак хранится в результате броска (`roll.hidden`), схема не менялась.
Бросать скрыто может только ГМ.

### Подключение

Клиент попадает в рассылку сразу, как собран его снапшот, - до отправки.
Иначе всё, что случилось, пока снапшот летел, терялось: события сцены
это переживали (разрыв seq -> перезапрос), а чат без seq пропадал молча.
Событие, обогнавшее снапшот, клиент видит как разрыв seq и перезапрашивает
состояние. Отправка снапшота - внутри того же try, что и уборка: клиент,
ушедший посреди отправки, не остаётся в рассылке.

## Лист персонажа

**Форма, а не создатель персонажа.** Как лист в Roll20: игрок вписывает
значения руками, правила никто не проверяет. Создатель (выбор класса,
расы, автоматический пересчёт бонусов) - это вся система правил в коде:
её надо писать, поддерживать и обновлять под каждую редакцию, и она
противоречит принципу "никакой системы правил в ядре". Форма работает с
любым персонажем, включая хоумбрю, а правила остаются за столом.

- **Схема - данные, а не компоненты.** `web/src/sheets/dnd5e.ts` описывает,
  какие поля есть, где лежат и как подписаны. `CharacterSheet` рисует
  любую схему из нескольких видов блоков (поля, характеристики, список
  с отметками, таблица). Новая система - новый файл схемы.
- **Вкладки и два режима.** Лист для игры, а не только для заполнения:
  шапка (хиты с −/+, КД, скорость, инициатива) видна на любой вкладке,
  первая вкладка - всё, что нужно в бою. По умолчанию режим "игра" -
  значения без рамок полей, пустое скрыто; поля ввода - только в
  "Редактировать". Шапка и вкладки описаны в схеме (`summary`, `tabs`).
- **Умения, предметы, заклинания - карточки**: название, пара полей,
  описание. Добавлять и править их можно и в режиме "игра" - предмет
  нашли посреди сессии, искать кнопку "Редактировать" не нужно. Описание
  пишется в редакторе TipTap 2.x (жирный, курсив, списки, подзаголовок) -
  тот же, что в LSS, поэтому импортированные тексты правятся без потерь.
  Редактор грузится отдельным куском кода только при правке.
- **Броски из листа.** Клик по оружию - атака и урон (Shift - с
  преимуществом, Alt - с помехой). Клиент собирает только формулу
  (`1d20+10`, `1к8+4`) и подпись, бросает сервер командой `dice.roll` -
  правило "кубы только на сервере" не меняется. Как собрать формулу из
  строки, описано в схеме (`rolls` у таблицы), а не в компоненте. На широком экране
  лист оставляет чат видимым; на узком окно листа занимает доступную ширину,
  а для возврата к чату его можно закрыть.
- **Ресурсы и отдых.** У ресурса с максимумом в режиме "игра" - счётчик
  с −/+ (не ниже 0 и не выше максимума). "Короткий отдых" и "Долгий
  отдых" поднимают до максимума ресурсы с нужной отметкой; что какой
  отдых восстанавливает - в схеме (`counter.rests`), а не в коде. Отдых
  пишется в чат от имени игрока, чтобы мастер видел. Хиты отдых не трогает.
- **Токен и лист.** У токена `character_id`. Привязать можно токен,
  который тебе можно править, к листу, который тебе виден (игрок - к
  своему, ГМ - к любому); чужой лист - "нет такого персонажа". Сразу
  привязанный токен ставит кнопка «На карту» в списке листов (см. «Мобы
  и NPC»), а не только настройки пустого токена. На токене -
  полоска хитов и значок КД; что рисовать, говорит схема (`token`).
  **Видят их только владелец и ГМ**: сервер не шлёт хиты в токене, клиент
  берёт их из листов, которые ему и так пришли, - у остальных данных нет.
  Лист открывается двойным кликом по токену: одиночный клик выбирает и
  тащит, лист на каждом ходе мешал бы. Удалили лист - токен остаётся, без
  привязки.
- **Поиск по листу** - по всем вкладкам сразу: карточки (название, поля,
  текст описания), строки таблиц, навыки, поля.
- **Расчёты - только подсказки формы.** Модификатор характеристики
  (`floor((x-10)/2)`) и бонус навыка или спасброска: модификатор +
  мастерство × уровень владения (0 нет, 1 владение, 2 мастерство -
  удвоенный бонус; старые листы с true/false читаются как 1/0) (`bonus` у блока-списка в схеме,
  `sheets/bonus.ts`). Импорт из LSS переносит только владение, и без
  этого навыки после импорта шли с пустым бонусом. Ручное поле «свой
  бонус» главнее посчитанного - экспертизу, предметы и хоумбрю игрок
  вписывает сам, лист правил не знает. Считает клиент, сервер хранит
  флаги и числа; клик по навыку собирает формулу `1d20+10`, бросает
  сервер. Атаку и КД игрок по-прежнему пишет сам. Тест - `web/tests`
  (`npm test`, встроенный `node --test`, без новых пакетов).
- **Пределы чисел** (`min`/`max` в схеме: характеристика 1-30, уровень 1-20,
  бонус навыка −10…+30) - защита от опечатки (`+99` вместо `+9`), а не
  правило: с запасом под хоумбрю, правятся в файле схемы. Вне пределов и
  дробное форма не сохраняет. Сервер их не проверяет - это не защита от
  злоумышленника; от раздувания данных сервер защищает форма данных.
- **Сервер правил не знает.** `data` - JSON, `sheet_data.py` проверяет
  только форму: путь к полю из простых сегментов, значения - обычный
  JSON, размер и глубина ограничены. Схему на сервере не дублируем.
- **Правка по полям** (`set: {"путь.к.полю": значение}`), а не листом
  целиком: ГМ и игрок, правящие разные поля, не затирают друг друга.
  Таблицы (оружие, ресурсы) записываются целиком.
- **Списки и счётчики - отдельными командами.** `character.list` -
  добавить, изменить, удалить элемент списка по id (заклинания); id нового
  выдаёт сервер, два одновременных добавления не затирают друг друга.
  `character.counter` - число на дельту в границах 0…max_path: «потратить
  ячейку» - клиент шлёт −1, сколько осталось, считает сервер по своим
  данным. Обе команды не знают, что за элементы и счётчики, - форма
  данных та же (`sheet_data`).
- **Видимость**: лист и все изменения уходят только владельцу и ГМ.
  Другим игрокам - ни при загрузке, ни в живых обновлениях. Чужой лист для
  игрока - "нет такого персонажа", а не "нельзя".

### Импорт из Long Story Short

Лист можно заполнить руками или импортировать JSON в формате Long Story
Short (`jsonType: "character"`, `version: "2"`) - его отдаёт кнопка
"скачать" на mycharacterbuilder.com и сам LSS.

- **Импорт формата, а не интеграция с сайтом.** У mycharacterbuilder.com
  и LSS нет открытого API для такого, а ходить на чужой сайт за игрока
  (логины, скрейпинг) - хрупко и сомнительно. Файл игрок скачивает сам и
  сам решает, что отдать. Формат - единственная точка связи: сайт может
  поменяться, файл на руках у игрока останется.
- **Своя схема, а не LSS как есть.** Адаптер `server/app/importers/lss.py`
  переводит файл в схему листа Laterna. Формат LSS версионирован и
  поменяется; если сделать его внутренним, его версия стала бы версией
  нашего листа, а ручная форма и другие источники подстраивались бы под
  чужие решения. Исходный файл хранится рядом с листом целиком
  (`source_json`): поменялся адаптер - "Переимпортировать" прогонит файл
  заново. Значения, которые есть в файле (хиты, характеристики, владения,
  оружие и ресурсы из файла), заменяются - ради этого переимпорт и
  запускают; интерфейс предупреждает. Вписанное игроком сверх файла
  остаётся: поля «О персонаже», заметки, портрет, свой бонус навыка, свои
  карточки и строки (`lss.merge_reimport`). Импортированные строки и
  карточки помечены `source: "lss"`, свои - нет; у старых листов без
  пометки строки из файла узнаются по id или имени, без дублей.
- **Тексты едут с персонажем, правил в ядре нет.** Разделы текстов из
  файла становятся карточками умений (снаряжение - карточкой предмета,
  предыстория, внешность, черты, союзники, задания и заметки - карточками
  «Записи» на вкладке «О персонаже») с описанием-документом TipTap. Не
  полями textarea: в LSS это документы со списками и жирным, в textarea они
  потеряли бы вид; а поля «История», «Внешность», «Черты характера»... -
  для своего текста игрока, импорт их не пишет; id карточки - из ключа LSS, так что
  переимпорт даёт те же карточки, а не дубли. Сервер их не понимает и не исполняет: "Второе дыхание
  восстанавливает 1к10 + уровень" - это текст для игрока, а не код.
  Адаптер переносит значения из поля в поле и ничего не считает (бонусы
  навыков, например, не выводит).
- **Два источника - один формат.** longstoryshort.app и
  mycharacterbuilder.com отдают `jsonType: character`, `version: 2`, но
  заполняют по-разному (образцы - `server/tests/fixtures/lss_nilon_app.json` и
  `lss_sad_mcb.json`). Адаптер по-прежнему только переносит:
  - урон «1 д8 +4 рубящий +1д6 сияющий» - бросаемое (кубы и числа) в
    формулу, слова в тип; не выделилось - текст заметкой, без кнопки;
  - оружие без `mod` - атака пустая (не выдумываем), `ability` и
    владение сохраняются, лист показывает «посчитано», ручное главнее;
  - ресурсы: удалённое (`isDeleted`, `orphanedAt`) не переносим; лежащее
    в снаряжении - карточками предметов (количество, описание), id
    ресурса сохраняется - на него ссылаются фишки в тексте «Снаряжение»;
    счётчики остаются счётчиками, `current > max` не обрезаем;
  - аватар - ссылка на их сервер: не скачиваем и не храним, в отчёте
    «портрет не перенесён»;
  - `isProf` 0/1/2 - уровень владения: 2 - мастерство (удвоенный бонус).
  - предыстория длиннее 60 символов или из нескольких предложений - не
    название, а история: уходит в «Историю персонажа», название пустое;
    одинаковый текст из раздела background не дублируется. Поля «О
    персонаже» при переимпорте - своё игрока главнее файла.
  Импорт возвращает отчёт (что перенесено, что нет) - одна строка в
  интерфейсе после загрузки, только тому, кто импортировал.
- **Проверки:** файл не больше 512 КБ; `jsonType`/`version` сверяются, и
  неизвестная версия - понятная ошибка, а не падение; поле `data` - JSON
  строкой внутри JSON, разбирается вторым `json.loads`; числа вне пределов
  схемы обрезаются до границы. Тест на образце - `server/tests/test_lss.py`.
- **Тексты - XSS-граница.** Файл присылает игрок, а текст увидит вся
  кампания. Поэтому два слоя. Сервер (`richtext.py`) пропускает каждый
  документ TipTap - и из импорта, и из редактора (любой `{"type": "doc"}`
  в `character.update`) - через белый список: абзацы, списки, заголовок,
  перенос, горизонтальная черта (`divider` из LSS хранится как
  `horizontalRule` - имя TipTap), текст с bold/italic/link, ссылки на
  ресурсы листа; остальное выбрасывает. Ссылка - только `https://` с
  хостом, без пробелов и кавычек; хранится один `href`. `javascript:`,
  `data:`, `http:`, `//` - марка выбрасывается, текст остаётся.
  `rel="noopener noreferrer"` и `target="_blank"` ставит клиент при
  отрисовке, из файла их не берём; клиент проверяет href ещё раз (React
  `javascript:` в href не блокирует). Клиент (`RichText.tsx`) рисует узлы React-элементами по
  такому же списку; редактор включает только эти узлы, а документ перед
  загрузкой в него проходит тот же список (`richDoc.ts`). `innerHTML` и
  `dangerouslySetInnerHTML` в проекте запрещены.

### Ссылки и dnd.su

У заклинаний и предметов есть поле "ссылка": игрок сам вставляет ссылку,
например на dnd.su. Принимаются только `https`, открываются в новой
вкладке с `rel="noopener noreferrer"`. Проверка стоит там, где ссылка
**рисуется**: лист приходит и из формы, и из файла игрока, и `javascript:`
в href выполнился бы у всех, кто откроет лист.

Контент dnd.su - переводы книг Wizards of the Coast. Копировать его в
проект нельзя, только ссылаться. Публичного поиска у dnd.su нет: адреса
не угадываем и сайт не скрейпим - ссылку вставляет игрок.

## Роли

Две роли: ГМ и игрок - флаг `is_gm` у аккаунта. Модель как в Foundry:
**публичной регистрации нет**. Открытая регистрация на сервере для своей
группы не нужна и только добавляет мусорные аккаунты.

### Приглашения

Аккаунт появляется только по одноразовой ссылке от мастера
(`?invite=<код>`), но **имя и пароль игрок придумывает сам**. Мастер не
должен знать пароли игроков: тот же пароль у человека может стоять и
где-то ещё. Поэтому и "забыл пароль" - тоже ссылка, а не пароль,
который мастер вбивает за игрока.

- Код - 32 случайных байта, в базе только sha256. Сам код уходит один раз,
  в `reply` мастеру, который его создал; в списке у ГМ - только срок.
- Ссылка одноразовая и живёт 7 дней. Принятая, отозванная и просроченная
  отвечают одинаково: "не найдено или истекло".
- Сброс пароля по ссылке закрывает все прежние сессии игрока и его
  открытые сокеты: если пароль меняют из-за чужого входа, чужой вылетает.
- Ссылку открыли - её экран важнее текущей сессии в браузере: её
  открывают, чтобы завести аккаунт, а не продолжить чужой вход.
- Эндпоинты `/api/invite/info` и `/api/invite/accept` - REST, а не команды
  сокета: у приглашённого ещё нет сессии, а сокет пускает только с ней.

### Вход и сессии

- Пароли - только argon2id (`argon2-cffi`). Открытыми не хранятся и не
  логируются. Хеширование - в отдельном потоке: argon2 намеренно медленный,
  и вход одного игрока не должен замораживать сокеты остальных.
- На "нет такого имени" и "неверный пароль" - один ответ, и пароль
  проверяется даже для несуществующего имени (против фиктивного хеша):
  иначе по ответу или по времени было бы видно, какие имена есть.
- Сессия - случайный токен в **httpOnly** cookie (скрипт страницы его не
  прочтёт), `SameSite=Lax` (чужой сайт не отправит от имени игрока ни POST,
  ни websocket). В базе - только sha256 токена: утёкшая база не даёт
  войти чужими сессиями.
- Срок сессии (30 дней) проверяет и сервер, а не только браузер по
  `max_age` cookie: украденный токен можно слать и после срока. Просроченная
  сессия удаляется при первой же попытке входа с ней.
- Выход закрывает сокеты **этой** сессии (другие вкладки того же браузера
  уходят на экран входа), но не другие входы игрока - телефон, второй
  компьютер. Для этого в `Actor` лежит хеш сессии.
- `Actor` (id, имя, `is_gm`) берётся только из сессии. Имени в адресе
  сокета больше нет: его мог подставить любой.
- Websocket проверяет заголовок `Origin`: браузер шлёт cookie на сокет с
  любой страницы, и чужой сайт мог бы открыть его от имени игрока.
  Пускаем адреса из `FRONTEND_URL` (можно несколько через запятую) и
  страницу с того же адреса, куда идёт сокет (`Origin` == `Host`) - иначе
  отвалились бы `127.0.0.1` и адрес в локальной сети, по которому заходят
  игроки. Без `Origin` - не браузер (скрипты, smoke_test); чужой сайт в
  браузере `Origin` шлёт всегда.
- `<meta name="referrer" content="no-referrer">`: ссылки ГМ и приглашения
  несут секрет в адресе, и он не должен уходить в `Referer` на внешние сайты.
- Удалённого игрока сервер выгоняет сразу: шлёт `campaign` без него и
  закрывает его сокеты. Его токены и стены переходят мастеру, а не
  становятся общими - общий токен может двигать кто угодно.

Не сделано: ограничение попыток входа, HTTPS (cookie без `Secure`, потому
что локально всё по http), смена пароля самим игроком.

### Ограничение попыток входа

`/api/login` и `/api/gm/login`: 5 неудач за 10 минут по паре «адрес +
имя» (для ключа ГМ имя - «ключ ГМ»), 30 за час по имени с любого адреса и
20 за 10 минут по одному адресу, потом 429 с `Retry-After`. Счётчика по
адресу нет для loopback (127.0.0.1, ::1): через Porthole или туннель без
X-Forwarded-For так приходят все игроки, и один ошибившийся паролем
заблокировал бы весь стол. Счётчики в памяти процесса (`ratelimit.py`), без
зависимостей: у мастера один процесс, перезапуск их обнуляет - приемлемо.
Проверка - до argon2, чтобы перебор не гонял дорогой хеш. Успешный вход
сбрасывает счётчик пары.

- За туннелем все приходят с 127.0.0.1. Настоящий адрес - в
  X-Forwarded-For, но его подделывает кто угодно, поэтому он учитывается
  только при `LANTERNA_TRUST_PROXY=1` и только для запросов с этой же
  машины, и берётся последний адрес (его дописал прокси). `./laterna.sh
  tunnel` включает это сам.
- Блок по паре «адрес + имя» позволяет чужому заблокировать вход игроку на
  10 минут (за туннелем без X-Forwarded-For адрес у всех общий). Это
  меньшее зло, чем подбор пароля.
- `LANTERNA_GM_KEY` короче 16 символов - предупреждение при старте:
  ключ даёт полный доступ к серверу.

### Локальный адрес прав не даёт

Через Porthole (и туннель) любой удалённый игрок для сервера мастера -
127.0.0.1. Поэтому от адреса клиента не зависит ничего, что даёт права.
Где адрес вообще встречается:

- **Кто вошёл и мастер ли он** - только сессия (cookie → запись в базе,
  `is_gm` у пользователя). Адрес не смотрится нигде.
- **Вход мастера** - только ключ (`/api/gm/login`, сравнение
  `compare_digest`), лимит попыток как у паролей. Первый вход тоже по ключу.
- **Лимит попыток входа** - единственное место, где адрес учитывается:
  счётчики «адрес + имя» и «имя»; счётчика по адресу для loopback нет.
- **X-Forwarded-For** учитывает только наш `client_ip` и только при
  `LANTERNA_TRUST_PROXY=1` (его ставит `./laterna.sh tunnel`; режим
  porthole его принудительно выключает). uvicorn запускается с
  `--no-proxy-headers`: сам он по умолчанию верил бы этому заголовку от
  127.0.0.1, и игрок через Porthole подменял бы свой адрес.
- **Origin сокета** - защита от чужого сайта, не права: пускает адреса из
  `FRONTEND_URL`, страницу с того же адреса и loopback-страницу к
  loopback-серверу с любым портом. Кто подключился, решает сессия.
- **Клиент** - `location.hostname === "localhost"` только для подсказки
  про адрес в приглашении.
- Cookie у браузера общие для 127.0.0.1 на всех портах: если игрок
  держит у себя ещё один Laterna на 127.0.0.1, сессии перезапишут друг
  друга (выйти и войти заново).

### Ключ ГМ

Ключ - способ **первого входа мастера**: по ссылке с ключом он создаёт
свой аккаунт (имя и пароль), дальше входит как все. Если пароль забыт,
ссылка с ключом снова пускает мастером: кто знает ключ, тот и так
владеет сервером.

- Ключ задаётся `LANTERNA_GM_KEY` или создаётся при первом запуске в
  `server/gm_key.txt` (не в git). Файл, а не новый ключ на каждый старт:
  `uvicorn --reload` перезапускается на каждую правку, ГМ терял бы права.
- Ссылку `...?gm=<ключ>` сервер печатает **только в момент создания
  ключа**, на остальных стартах - путь к файлу. Лог печатается на каждый
  перезапуск (с `--reload` это каждая правка), а логи вставляют в чаты.
  Ссылку по запросу даёт `./dev.sh gm`.
- Клиент забирает ключ из адресной строки при загрузке и сразу убирает
  его оттуда, обменивает на сессию и больше не хранит.

Хендлеры проверяют права по `Actor` сами. Клиент знает свою роль только
чтобы показать или спрятать инструменты.

Что сейчас только у ГМ: `scene.update` (карта, клетка, размер сцены),
загрузка файлов, стены, сцены, игроки, чужие токены.

### Права

Одно правило на всё: **своё правит владелец, чужое - только ГМ**.
Проверяет `_require_owner` в handlers.py, ГМ она пропускает. Мастер
ведёт партию и убирает за всеми, а игрок не должен портить чужое -
даже случайно. Двигать тоже: своего персонажа ходит игрок, монстров
и чужих - мастер.

Кроме владения:

- **Стены ставит только ГМ.** Это разметка карты. Игрок со стенами мог
  бы запереть других или отгородиться от монстров. Инструменты «Стена» и
  «Стереть» игроку не показываются.
- **Владельца токена меняет только ГМ.** Иначе игрок сделал бы свой
  токен общим (`owner = null`) или "подарил" его, и правила выше
  перестали бы что-то значить.
- **Загружать картинки может любой вошедший** - игрок ставит картинку
  своего токена сам. Лимит игрока 5 МБ, мастера 25 МБ: игроки не забьют
  диск. Что можно сделать с файлом, решают команды: картой сцены его
  ставит только ГМ, картинкой токена - тот, кто может править токен.
- **Картинки - только загруженные файлы.** `image_url` токена и фон сцены
  проверяет одна функция `_upload_url`: адрес вида `/uploads/<hex>.<ext>`
  и файл реально существует. Произвольный URL заставил бы браузеры всех
  игроков ходить на чужой сервер.

Это не противоречит правилу «отменять можно только своё»: Ctrl+Z
по-прежнему убирает только стены этого клиента. Удаление чужого - явное
действие ГМ (режим «Стереть», Delete на выбранном), а не горячая
клавиша отмены.

## Что осознанно отложено

- Динамическое освещение и полигоны видимости - после того, как по карте можно будет просто играть.
- Туман войны с сохранением.
- Автоматика правил в листе персонажа (пересчёт бонусов, выбор класса). Лист - форма, см. "Лист персонажа".
- Голос, LiveKit.
- Ограничение попыток входа и HTTPS. Аккаунты и сессии есть, но перебор паролей ничем, кроме медленного argon2, не тормозится, а cookie без `Secure`.
- Несколько кампаний у одного мастера. Модель готова (всё привязано к
  Campaign), не хватает выбора кампании и кампании в адресе. Открытый
  вопрос: аккаунт на кампанию (как сейчас) или на сервер с ролью в
  каждой кампании. Решить до появления реальных пользователей.
- Генератор событий в духе RimWorld Director. Делается поздно, но почти не зависит от канваса, так что может идти параллельно.
- Порядок до освещения: редактор стен/дверей/окон -> видимость
  токена -> источники света -> туман войны. Свет считается от стен,
  без них его не на чем проверять.
- Импорт Universal VTT (.uvtt, .dd2vtt, .df2vtt - один формат):
  картинка, клетка, стены, порталы, свет. Ложится на нашу модель:
  дверь/окно = kind, барьер = стена с blocks_sight=false. Нужна
  сущность Light (позиция, радиус, цвет, яркость). Может идти раньше
  собственного редактора - даёт размеченные стены для отладки света.
- Фигуры (Drawing: тип, точки, заливка, слой), галочка "фигура
  создаёт стены". Кисть - векторные мазки с упрощением, не растр.
- Ассеты: главное - библиотека с загрузкой паков мастера. Стартовый
  набор - процедурное (кровь, трава, земля), CC0 (Kenney), сгенери-
  рованное только с пометкой. Чужие паки в репозиторий не класть:
  большинство лицензий запрещает распространение.
- Перевод: строки интерфейса в ru.json/en.json, сервер шлёт коды
  ошибок (wall_blocked, gm_only), а не текст. Кубы понимают d и к.
- Лист персонажа: форма + импорт LSS (своя схема, LSS - через
  адаптер). dnd.su - только ссылки, которые вставляет игрок: контент
  там - переводы книг WotC, парсить и копировать нельзя.
  Создатель персонажа с проверкой правил - не делаем.
- Запуск одной командой, фронт и API на одном порту, туннель
  (Cloudflare Tunnel) вместо проброса портов.
## Стек

- Бэкенд: Python 3.12, FastAPI, SQLAlchemy 2 async, Postgres (SQLite как fallback для локального запуска без docker)
- Фронтенд: React 18, TypeScript, Vite, PixiJS 8 для сцены, zustand для состояния
- Инфра: docker compose

### Один порт для игры

`./laterna.sh` - один процесс uvicorn на :8000: и API, и собранный фронт
(`web/dist`). Мастеру не нужно держать два процесса и объяснять игрокам
два порта; для туннеля это тоже один адрес. vite с горячей перезагрузкой
- только для разработки (`./dev.sh`).

- Фронт сервер отдаёт, только если `web/dist/index.html` есть
  (`WEB_DIST`). Нет сборки - чистый API, как раньше.
- Маршрут `/{path}` подключён последним и ловит всё, что не API: так
  перезагрузка страницы на любом адресе отдаёт приложение. `/api/...`,
  `/ws/...`, `/uploads/...` мимо него - неизвестный API остаётся 404.
- Путь к файлу проверяется после `resolve()` - `../` не выводит из dist.
- Проверка Origin сокета уже пускает страницу с того же адреса, что и
  сокет, - отдельной настройки для одного порта не нужно.

### Туннель

`./laterna.sh tunnel` - cloudflared quick tunnel: без аккаунта, без
проброса портов, адрес `https://…trycloudflare.com`. Выбран потому, что
мастеру не надо ничего регистрировать и настраивать, а HTTPS до игрока
даёт Cloudflare - пароли не идут по сети открытым текстом.

- Адрес случайный и живёт, пока запущен скрипт. Постоянный адрес -
  именованный туннель со своим доменом, это уже настройка мастера, не
  ядра.
- Скрипт сначала поднимает туннель и ловит адрес из его вывода, потом
  сервер с `PUBLIC_URL`: мастер сидит на localhost, а приглашения должны
  вести на адрес из интернета. ГМ получает его в снапшоте (`you.public_url`),
  игрокам он не нужен.
- Адрес cloudflared печатает сразу, а к сети Cloudflare подключается
  позже - и может не подключиться (игрок получит ошибку 1033). Поэтому
  скрипт ждёт строки «Registered tunnel connection», а не адреса.
- Часть провайдеров режет туннели Cloudflare (порт 7844 и рукопожатие TLS
  с их серверами) - так было и на машине, где это писалось. Запасной путь
  - `TUNNEL_VIA=ssh`: обратный ssh-туннель на localhost.run, тоже HTTPS и
  без аккаунта, ssh есть почти везде.
- Бесплатные туннели медленные: localhost.run отдавал 15-30 КБ/с, и
  полмегабайта скрипта шли почти минуту - игрок видел пустой экран и
  думал, что всё зависло. Поэтому сервер сжимает ответы (gzip, скрипт
  втрое меньше), а index.html до загрузки показывает «Загружаю стол…».
- В России зарубежные туннели режут: соединение замирает после первых
  килобайт (index.html доходит, скрипт - нет). Это не лечится кодом -
  игрокам нужен VPN, либо туннель с выходом в России, либо общая
  виртуальная сеть вместо туннеля.
- Адрес туннеля скрипт добавляет в разрешённые Origin сокета
  (`FRONTEND_URL`): не каждый сервис туннелей передаёт серверу исходный
  Host, а без этого проверка Origin отбила бы игроков.
- Туннель открывает стол всему интернету. Вход по паролю (argon2), ключ
  ГМ длинный, но ограничения попыток входа пока нет - оно в бете, при
  игре через туннель его стоит поднять раньше.

React отвечает только за UI вокруг канваса. Внутрь сцены React не лезет - там императивный PixiJS. Смешивать эти две модели - верный способ получить тормоза и невоспроизводимые баги.

## Исправления синхронизации и интерфейса (01.11.2026)

Сервер отправляет heartbeat после 15 секунд без входящих команд. Клиент закрывает сокет после 45 секунд без сообщений и переподключается. Разрыв seq также вызывает новое подключение: HTTP-снимок больше не конкурирует с событиями сокета. Ошибка или таймаут отправки исключает соединение из хаба и закрывает его. Снимок при подключении повторно читается и отправляется под локом сцены.

Портрет передаётся отдельным публичным полем token.portrait_url, проверяется как локальная загрузка и применяется только при пустом image_url. Лист и хиты моба остаются закрытыми. Изменение портрета/удаление листа вызывает tokens_refresh: клиенты переподключаются за отфильтрованным снимком. Обычная правка хитов не требует переподключения.

hpChanges поглощает уменьшение текущих хитов временными одной командой character.update. Размещение персонажа сохраняет владельца листа. Alt отключает привязку только в клиентском перетаскивании; сервер по-прежнему проверяет стены. Модальное окно листа имеет собственный слой и сжимаемые колонки.

## Альфа: ввод и новая раскладка листа

Пинг на панели определяется возможностями ввода (`navigator.maxTouchPoints`, `(any-pointer: coarse)`), а не шириной экрана. У него значок мишени; Alt+клик на десктопе продолжает отправлять прежнюю команду ping. Alt+перетаскивание токена сохраняет свободное перемещение. Частота и автор пинга остаются серверными. Пользовательские инструменты и инструменты ГМ разделены группами; создание пустого токена скрыто у игрока, но команда/старые данные не удалены.

Чат не размонтируется при сворачивании: скрывается оболочка панели, черновик остаётся в Chat. Видимая кнопка возврата и отдельная кнопка скрытия имеют доступные подписи и 44px цели. На сенсорных устройствах они доступны и при широкой/горизонтальной раскладке; ResizeObserver Pixi продолжает следить за фактическим контейнером.

У привязанных токенов UI не предлагает менять image_url/character_id; серверные поля и прежние значения сохранены. Кнопка и двойной клик открывают видимый клиенту лист. У непривязанных объектов остаются загрузка картинки и первичная привязка. При отрисовке сохранённая image_url главнее portrait_url листа.

Схема dnd5e перенесла прежние checklist-блоки навыков и спасбросков на main. CharacterSheet объединяет их по объявленной связи item.ability и bonus.abilities с блоком характеристик; отдельно эти списки не дублируются. Поиск по-прежнему обходит исходные checklist-блоки схемы. AbilityChecks использует существующие checkBonus/profLevel и отправляет прежние character.update/dice.roll. JSON, серверная модель и пути abilities.<key>.score/save/save_bonus, skills.<key>.prof/bonus не меняются. Старое сохранённое имя вкладки skills приводит к первой вкладке main. Общая auto-fit/minmax-сетка и переносы элементов применяются к персонажу и мобу на всех ширинах, не скрывая недоступное содержимое через overflow:hidden.

## v0.1.2-alpha: папки сцен и визуализация бросков

`SceneFolder` принадлежит кампании, имеет имя и время создания. Только один уровень: у папки нет родителя. В `Scene` добавлены nullable `folder_id` (FK с ON DELETE SET NULL) и `sort_order`. Старые сцены остаются в корне; NULL-порядок сортируется по времени создания и id. `folder.create/rename/delete` и `scene.move` - команды кампании только для ГМ, под прежним локом кампании, с обычными `cmd_id`/reply/campaign, без изменения seq сцены. `scene.move` проверяет папку и сцену назначения в этой кампании, сохраняет порядок целевой группы; `folder.delete` явно переносит сцены в корень до удаления папки. Токены, стены, фон, бой и туман не меняются. Схема обновляется добавочно в `db._check_columns`: новая таблица и две nullable-колонки, без пересоздания старой таблицы. Поле родителя раньше было только пожеланием ROADMAP, в модели его не было. Листы персонажей не менялись.

ГМ получает `folders` и расширенный список `scenes` в прежнем сообщении `campaign`; игрок получает только активный id и список пользователей. Изменение имени или фона сцены также обновляет браузер сцен у подключённых ГМ. Карточки используют только `preview_url`, не загружают оригинальные неактивные карты и не создают Pixi-сцены. Свёрнутые группы запоминаются локально для пользователя. Порядок и распределение - только серверные данные.

`GET /api/scenes/{id}/preview` проверяет сессию, роль ГМ и кампанию; игроку - 403. Pillow декодирует только локальные загрузки с проверенным именем PNG/JPEG/WebP, не обращается к внешним URL. Исходник ограничен 40 млн пикселей, результат - WebP до 480×300. Генерация выполняется в worker thread, сериализована для ограничения памяти, файл записывается через временный файл и replace. Кэш расположен рядом с uploads, вне публичного mount; его можно удалить для повторной генерации. HTTP-ответ private/no-store повторно проверяет роль при каждом запросе, включая смену аккаунта в том же браузере. Отсутствующий или повреждённый фон получает тематическую заглушку; файл фона не изменяется. Pillow - единственная новая зависимость.

Кнопка «Кубики» на панели открывает немодальную `DiceMenu`, использующую ту же `dice.roll`, что лист и прежняя панель под чатом. Одна формула, 1–100 кубиков, d4/d6/d8/d10/d12/d20/d100 и модификатор; быстрый d20. Серверный парсер, secrets, Message и фильтрация скрытых бросков не изменены. Отдельные `terms[].rolls/kept`, формула и total уже присутствовали в событии.

`DiceAnimation` - временное представление разрешённого живого сообщения chat, а не состояние Pixi-сцены или новый движок бросков. Показывает только присланные значения: CSS-подброс/вращение, остановка через 700 мс, удаление DOM через 4,2 с. Одновременно только последний бросок, до 12 визуальных кубиков; остаток и полная история остаются в чате. У dropped/отрицательных кубиков сохраняется обозначение. Overlay имеет pointer-events:none, меню не модальное; перемещение токенов остаётся доступным. Таймеры отключаются при замене/размонтировании. Без новых frontend-зависимостей и физического движка.

Настройка анимации хранится в localStorage; на устройствах с hardwareConcurrency ≤ 2 по умолчанию выключена, явный выбор пользователя сохраняется. `prefers-reduced-motion: reduce` всегда отключает визуализацию. История из snapshot никогда не запускает анимацию; id живых сообщений дедуплицируются ограниченным набором до 512 записей. Секретный бросок доходит игроку как прежняя заглушка hidden_roll без roll и не может запустить анимацию. Переходы сцен, seq, fog и токены остаются в существующем протоколе и PixiJS.


### Дополнение v0.1.2-alpha: групповое выделение и удаление

`SceneStage` хранит Set выбранных id в PixiJS. Shift+клик переключает один id, Shift+рамка по пустому месту добавляет видимые токены, чьи центры внутри прямоугольника. Обычный клик заменяет группу одним токеном, клик по пустому месту/Esc снимает выбор. Shift+клик по двери у ГМ сохраняет прежнее запирание; линейка, туман и Alt-пинг не меняются. Групповое перетаскивание не добавлено.

Карточка показывается только для одного токена; у группы отдельная панель с количеством, числом доступных для удаления и кнопкой очистки. В Zustand передаются только два UI-счётчика, id/координаты/рамка остаются в Stage. Снимок, удаление и скрытие туманом убирают устаревшие id. Удержание Shift при клике не начинает движение токена.

Delete/Backspace или кнопка группы вызывают прежнюю `token.remove` для каждого доступного токена. Игрок - свои и общие, ГМ - любые; окончательные права и seq проверяет прежний серверный handler. Новых серверных команд/полей БД нет. Клиент ждёт событий удаления; при обрыве новый снимок показывает фактический результат, неподтверждённые удаления не повторяются. Delete при вводе в input/textarea/select/contenteditable не трогает выделение, повтор удерживаемой клавиши не рассылает команды заново.
