# Lanterna - архитектура

Рабочее название. Открытый self-hosted VTT. Переименовать можно в любой момент - имя нигде не зашито, кроме README и compose.

## Принципы

1. **Сервер - источник правды.** Клиент не меняет состояние сам, он шлёт команду. Сервер валидирует, применяет, рассылает событие. Клиент применяет событие.
2. **Клиент может применить оптимистично**, но помечает изменение как неподтверждённое и откатывает, если сервер прислал другое.
3. **Геометрия и рендер - на клиенте.** Python ничего не рисует и не считает полигоны видимости. Его работа: auth, хранение, валидация, рассылка, броски кубов.
4. **Стены существуют с первого дня**, даже пока свет не реализован. Переделывать схему сцены потом дороже, чем заложить поля сейчас.
5. **Никакой системы правил в ядре.** Лист персонажа - это JSON + схема полей. Хардкод одной системы появится позже, модульность - ещё позже, и только после того, как одна система заработает.

## Модель данных

```
Campaign           active_scene_id
  User             имя, argon2-хеш пароля, is_gm
    AuthSession    sha256 токена сессии
  Scene            грид, фон, размеры
    Layer          background | tokens | walls | gm
      Token        x, y, размер в клетках, картинка, owner_id, vision_range
      Wall         x1,y1,x2,y2 + флаги, owner_id
  Message          чат и броски, author + author_id
```

Владелец - **id пользователя, не имя**: имя можно сменить, а совпадение
имён ничего не должно значить.

### Wall - поля с первого дня

| поле | зачем |
|---|---|
| `blocks_movement` | токен не проходит |
| `blocks_sight` | перекрывает видимость (пока не используется) |
| `blocks_sound` | на будущее |
| `kind` | `wall` / `door` / `secret_door` / `window` / `invisible` |
| `door_state` | `closed` / `open` / `locked` |
| `owner_id` | кто поставил (id); удалить может он или ГМ. `null` - общая стена |

Сегодня работает только `blocks_movement`. Остальное лежит в БД и ждёт этапа освещения.

### Координаты

Всё хранится в **пикселях сцены**, а не в клетках. Сетка - это способ отображения и привязки, а не единица хранения. Иначе гексы и бессеточные карты потом не вставить.

## Протокол

Один websocket на сцену: `/ws/scene/{scene_id}`. Кто подключился, сервер
берёт из cookie сессии - в адресе о пользователе ничего нет. Без сессии
приходит `{ "type": "auth_required" }` и сокет закрывается (4401).

**Клиент -> сервер (команда):**
```json
{ "type": "cmd", "id": "uuid-клиента", "name": "token.move", "payload": {...} }
```

**Сервер -> клиент (событие):**
```json
{ "type": "event", "seq": 42, "name": "token.moved", "payload": {...}, "cmd_id": "uuid-клиента|null" }
```

**При подключении:**
```json
{ "type": "snapshot", "seq": 42, "scene": {...}, "you": { "id": "...", "name": "...", "is_gm": false } }
```

**Мимо seq сцены** (общее на кампанию, получают все подключённые):
```json
{ "type": "chat", "message": {...} }
{ "type": "campaign", "active_scene_id": "...", "scenes": [...], "users": [{ "id": "...", "name": "...", "is_gm": false }] }
{ "type": "reply", "name": "scene.created", "payload": {...}, "cmd_id": "..." }
```
`scenes` в `campaign` приходит только ГМ, `users` - всем (имена и так
видны в чате; клиенту они нужны, чтобы подписать, чей токен). `reply` -
ответ одному отправителю команды кампании.

`seq` - монотонный счётчик на сцену. Клиент хранит последний применённый seq. Если пришло событие с seq <= текущего, игнорирует (повтор). Если разрыв - перезапрашивает снапшот. Это дешёвая замена полноценному event sourcing и её хватит надолго.

`cmd_id` возвращается, чтобы клиент понял, какое из его оптимистичных изменений подтвердилось.

### Команды

Сцены (событие с seq, рассылается в комнату сцены):

| команда | событие | кто |
|---|---|---|
| `token.add` | `token.added` | все |
| `token.move` | `token.moved` | владелец или ГМ |
| `token.update` | `token.updated` | владелец или ГМ |
| `token.remove` | `token.removed` | владелец или ГМ |
| `wall.add` | `wall.added` | ГМ |
| `wall.remove` | `wall.removed` | владелец или ГМ |
| `scene.update` | `scene.updated` | ГМ |

Кампании (без seq, `handle_campaign` в main.py):

| команда | что уходит | кто |
|---|---|---|
| `chat.say` | `chat` всем | все |
| `scene.create` | `reply` + `campaign` | ГМ |
| `scene.activate` | `campaign`, игроки переезжают | ГМ |
| `scene.delete` | `campaign` | ГМ, не активную |
| `player.create` | `reply` + `campaign` | ГМ |
| `player.password` | `reply`, сессии игрока закрываются | ГМ, не себе |
| `player.delete` | `campaign`, сокеты игрока закрываются | ГМ, не себя |

### Сцены и что видят игроки

Игрок видит только активную сцену кампании (`active_scene_id`), ГМ -
любую. Остальные сцены - заготовки, и **сервер их игроку не отдаёт
вообще**: ни сокет, ни REST-снапшот, ни список. Прятать на клиенте
нельзя - всё, что пришло в браузер, видно в DevTools.

Когда ГМ показывает другую сцену, сервер шлёт игрокам `campaign` и сам
закрывает их сокеты в старой сцене. Клиент по `campaign` переподключается
в новую. Полагаться на то, что клиент уйдёт сам, нельзя.

Чат общий на кампанию, а не на сцену: ГМ в заготовке видит игроков, а
смена сцены не стирает историю бросков. Поэтому он идёт мимо seq сцены -
иначе сообщение из чужой сцены выглядело бы для клиента разрывом нумерации.

### Броски кубов - только на сервере

Клиент шлёт строку `2d6+3`. Сервер парсит, бросает, рассылает результат вместе с отдельными кубами. Клиент никогда не генерирует случайное число для броска. Иначе любой игрок с девтулзами крутит d20 как хочет.

## Роли

Две роли: ГМ и игрок - флаг `is_gm` у аккаунта. Модель как в Foundry:
**публичной регистрации нет**. Игроков заводит мастер внутри кампании,
задаёт имя и пароль. Открытая регистрация на сервере для своей группы
не нужна и только добавляет мусорные аккаунты.

### Вход и сессии

- Пароли - только argon2id (`argon2-cffi`). Открытыми не хранятся и не
  логируются. Хеширование - в отдельном потоке: argon2 намеренно медленный,
  и вход одного игрока не должен замораживать сокеты остальных.
- На "нет такого имени" и "неверный пароль" - один ответ, и пароль
  проверяется даже для несуществующего имени (против фиктивного хеша):
  иначе по ответу или по времени было бы видно, какие имена есть.
- Сессия - случайный токен в **httpOnly** cookie (скрипт страницы его не
  прочтёт), `SameSite=Lax` (чужой сайт не отправит от имени игрока ни POST,
  ни websocket). В базе - только sha256 токена: утёкшая база не даёт
  войти чужими сессиями.
- `Actor` (id, имя, `is_gm`) берётся только из сессии. Имени в адресе
  сокета больше нет: его мог подставить любой.
- Удалённого игрока сервер выгоняет сразу: шлёт `campaign` без него и
  закрывает его сокеты. Его токены и стены переходят мастеру, а не
  становятся общими - общий токен может двигать кто угодно.

Не сделано: ограничение попыток входа, HTTPS (cookie без `Secure`, потому
что локально всё по http), смена пароля самим игроком.

### Ключ ГМ

Ключ - способ **первого входа мастера**: по ссылке с ключом он создаёт
свой аккаунт (имя и пароль), дальше входит как все. Если пароль забыт,
ссылка с ключом снова пускает мастером: кто знает ключ, тот и так
владеет сервером.

- Ключ задаётся `LANTERNA_GM_KEY` или создаётся при первом запуске в
  `server/gm_key.txt` (не в git). Файл, а не новый ключ на каждый старт:
  `uvicorn --reload` перезапускается на каждую правку, ГМ терял бы права.
- Ссылку `...?gm=<ключ>` сервер печатает **только в момент создания
  ключа**, на остальных стартах - путь к файлу. Лог печатается на каждый
  перезапуск (с `--reload` это каждая правка), а логи вставляют в чаты.
  Ссылку по запросу даёт `./dev.sh gm`.
- Клиент забирает ключ из адресной строки при загрузке и сразу убирает
  его оттуда, обменивает на сессию и больше не хранит.

Хендлеры проверяют права по `Actor` сами. Клиент знает свою роль только
чтобы показать или спрятать инструменты.

Что сейчас только у ГМ: `scene.update` (карта, клетка, размер сцены),
загрузка файлов, стены, сцены, игроки, чужие токены.

### Права

Одно правило на всё: **своё правит владелец, чужое - только ГМ**.
Проверяет `_require_owner` в handlers.py, ГМ она пропускает. Мастер
ведёт партию и убирает за всеми, а игрок не должен портить чужое -
даже случайно. Двигать тоже: своего персонажа ходит игрок, монстров
и чужих - мастер.

Кроме владения:

- **Стены ставит только ГМ.** Это разметка карты. Игрок со стенами мог
  бы запереть других или отгородиться от монстров. Инструменты «Стена» и
  «Стереть» игроку не показываются.
- **Владельца токена меняет только ГМ.** Иначе игрок сделал бы свой
  токен общим (`owner = null`) или "подарил" его, и правила выше
  перестали бы что-то значить.
- **Картинки - только загруженные файлы.** `image_url` токена и фон сцены
  проверяет одна функция `_upload_url`: адрес вида `/uploads/<hex>.<ext>`
  и файл реально существует. Произвольный URL заставил бы браузеры всех
  игроков ходить на чужой сервер.

Это не противоречит правилу «отменять можно только своё»: Ctrl+Z
по-прежнему убирает только стены этого клиента. Удаление чужого - явное
действие ГМ (режим «Стереть», Delete на выбранном), а не горячая
клавиша отмены.

## Что осознанно отложено

- Динамическое освещение и полигоны видимости - после того, как по карте можно будет просто играть.
- Туман войны с сохранением.
- Листы персонажей.
- Голос, LiveKit.
- Ограничение попыток входа и HTTPS. Аккаунты и сессии есть, но перебор паролей ничем, кроме медленного argon2, не тормозится, а cookie без `Secure`.
- Генератор событий в духе RimWorld Director. Делается поздно, но почти не зависит от канваса, так что может идти параллельно.

## Стек

- Бэкенд: Python 3.12, FastAPI, SQLAlchemy 2 async, Postgres (SQLite как fallback для локального запуска без docker)
- Фронтенд: React 18, TypeScript, Vite, PixiJS 8 для сцены, zustand для состояния
- Инфра: docker compose

React отвечает только за UI вокруг канваса. Внутрь сцены React не лезет - там императивный PixiJS. Смешивать эти две модели - верный способ получить тормоза и невоспроизводимые баги.
