# Lanterna - архитектура

Рабочее название. Открытый self-hosted VTT. Переименовать можно в любой момент - имя нигде не зашито, кроме README и compose.
## Зачем этот проект

Бесплатный VTT, который мастер поднимает у себя. Цель - закрыть то,
за что приходится платить или терпеть в других:
- Roll20: свет и стены работают только по подписке, неудобный интерфейс
- Foundry: $50 разово, но главный барьер - хостинг у мастера
- Owlbear Rodeo: бесплатный и простой, свет есть через официальное
  расширение. Главный конкурент. Отличаться от него: открытый код и
  свой сервер, русский язык, импорт персонажей из LSS, Режиссёр событий
Перед новой большой фичей спросить: решает ли она одну из этих проблем.
## Принципы

1. **Сервер - источник правды.** Клиент не меняет состояние сам, он шлёт команду. Сервер валидирует, применяет, рассылает событие. Клиент применяет событие.
2. **Клиент может применить оптимистично**, но помечает изменение как неподтверждённое и откатывает, если сервер прислал другое.
3. **Геометрия и рендер - на клиенте.** Python ничего не рисует и не считает полигоны видимости. Его работа: auth, хранение, валидация, рассылка, броски кубов.
4. **Стены существуют с первого дня**, даже пока свет не реализован. Переделывать схему сцены потом дороже, чем заложить поля сейчас.
5. **Никакой системы правил в ядре.** Лист персонажа - это JSON + схема полей. Хардкод одной системы появится позже, модульность - ещё позже, и только после того, как одна система заработает.

## Модель данных

```
Campaign           active_scene_id
  User             имя, argon2-хеш пароля, is_gm
    AuthSession    sha256 токена сессии
  Scene            грид, фон, размеры
    Layer          background | tokens | walls | gm
      Token        x, y, размер в клетках, картинка, owner_id, vision_range
      Wall         x1,y1,x2,y2 + флаги, owner_id
  Message          чат и броски, author + author_id
  Character        owner_id, name, system, data (JSON по схеме), исходник импорта
```

Владелец - **id пользователя, не имя**: имя можно сменить, а совпадение
имён ничего не должно значить.

### Wall - поля с первого дня

| поле | зачем |
|---|---|
| `blocks_movement` | токен не проходит |
| `blocks_sight` | перекрывает видимость (пока не используется) |
| `blocks_sound` | на будущее |
| `kind` | `wall` / `door` / `secret_door` / `window` / `invisible` |
| `door_state` | `closed` / `open` / `locked` |
| `owner_id` | кто поставил (id); удалить может он или ГМ. `null` - общая стена |

Сегодня работает только `blocks_movement`. Остальное лежит в БД и ждёт этапа освещения.

### Координаты

Всё хранится в **пикселях сцены**, а не в клетках. Сетка - это способ отображения и привязки, а не единица хранения. Иначе гексы и бессеточные карты потом не вставить.

## Протокол

Один websocket на сцену: `/ws/scene/{scene_id}`. Кто подключился, сервер
берёт из cookie сессии - в адресе о пользователе ничего нет. Без сессии
приходит `{ "type": "auth_required" }` и сокет закрывается (4401).

**Клиент -> сервер (команда):**
```json
{ "type": "cmd", "id": "uuid-клиента", "name": "token.move", "payload": {...} }
```

**Сервер -> клиент (событие):**
```json
{ "type": "event", "seq": 42, "name": "token.moved", "payload": {...}, "cmd_id": "uuid-клиента|null" }
```

**При подключении:**
```json
{ "type": "snapshot", "seq": 42, "scene": {...}, "you": { "id": "...", "name": "...", "is_gm": false } }
```

**Мимо seq сцены** (общее на кампанию, получают все подключённые):
```json
{ "type": "chat", "message": {...} }
{ "type": "campaign", "active_scene_id": "...", "scenes": [...], "users": [{ "id": "...", "name": "...", "is_gm": false }] }
{ "type": "reply", "name": "scene.created", "payload": {...}, "cmd_id": "..." }
```
`scenes` в `campaign` приходит только ГМ, `users` - всем (имена и так
видны в чате; клиенту они нужны, чтобы подписать, чей токен). `reply` -
ответ одному отправителю команды кампании.

`seq` - монотонный счётчик на сцену. Клиент хранит последний применённый seq. Если пришло событие с seq <= текущего, игнорирует (повтор). Если разрыв - перезапрашивает снапшот. Это дешёвая замена полноценному event sourcing и её хватит надолго.

`cmd_id` возвращается, чтобы клиент понял, какое из его оптимистичных изменений подтвердилось.

### Команды

Сцены (событие с seq, рассылается в комнату сцены):

| команда | событие | кто |
|---|---|---|
| `token.add` | `token.added` | все |
| `token.move` | `token.moved` | владелец или ГМ |
| `token.update` | `token.updated` | владелец или ГМ |
| `token.remove` | `token.removed` | владелец или ГМ |
| `wall.add` | `wall.added` | ГМ |
| `wall.remove` | `wall.removed` | владелец или ГМ |
| `scene.update` | `scene.updated` | ГМ |

Кампании (без seq, `handle_campaign` в main.py):

| команда | что уходит | кто |
|---|---|---|
| `chat.say` | `chat` всем | все |
| `scene.create` | `reply` + `campaign` | ГМ |
| `scene.activate` | `campaign`, игроки переезжают | ГМ |
| `scene.delete` | `campaign` | ГМ, не активную |
| `invite.create` | `reply` с кодом (только ему) + `campaign` | ГМ |
| `invite.revoke` | `campaign` | ГМ |
| `player.delete` | `campaign`, сокеты игрока закрываются | ГМ, не себя |
| `character.create` | `reply` + `character` владельцу и ГМ | все (себе), ГМ - кому угодно |
| `character.update` | `character` владельцу и ГМ | владелец или ГМ |
| `character.delete` | `character_deleted` владельцу и ГМ | владелец или ГМ |

### Сцены и что видят игроки

Игрок видит только активную сцену кампании (`active_scene_id`), ГМ -
любую. Остальные сцены - заготовки, и **сервер их игроку не отдаёт
вообще**: ни сокет, ни REST-снапшот, ни список. Прятать на клиенте
нельзя - всё, что пришло в браузер, видно в DevTools.

Когда ГМ показывает другую сцену, сервер шлёт игрокам `campaign` и сам
закрывает их сокеты в старой сцене. Клиент по `campaign` переподключается
в новую. Полагаться на то, что клиент уйдёт сам, нельзя.

Чат общий на кампанию, а не на сцену: ГМ в заготовке видит игроков, а
смена сцены не стирает историю бросков. Поэтому он идёт мимо seq сцены -
иначе сообщение из чужой сцены выглядело бы для клиента разрывом нумерации.

### Броски кубов - только на сервере

Клиент шлёт строку `2d6+3`. Сервер парсит, бросает, рассылает результат вместе с отдельными кубами. Клиент никогда не генерирует случайное число для броска. Иначе любой игрок с девтулзами крутит d20 как хочет.

## Лист персонажа

**Форма, а не создатель персонажа.** Как лист в Roll20: игрок вписывает
значения руками, правила никто не проверяет. Создатель (выбор класса,
расы, автоматический пересчёт бонусов) - это вся система правил в коде:
её надо писать, поддерживать и обновлять под каждую редакцию, и она
противоречит принципу "никакой системы правил в ядре". Форма работает с
любым персонажем, включая хоумбрю, а правила остаются за столом.

- **Схема - данные, а не компоненты.** `web/src/sheets/dnd5e.ts` описывает,
  какие поля есть, где лежат и как подписаны. `CharacterSheet` рисует
  любую схему из нескольких видов блоков (поля, характеристики, список
  с отметками, таблица). Новая система - новый файл схемы.
- **Вкладки и два режима.** Лист для игры, а не только для заполнения:
  шапка (хиты с −/+, КД, скорость, инициатива) видна на любой вкладке,
  первая вкладка - всё, что нужно в бою. По умолчанию режим "игра" -
  значения без рамок полей, пустое скрыто; поля ввода - только в
  "Редактировать". Шапка и вкладки описаны в схеме (`summary`, `tabs`).
- **Умения, предметы, заклинания - карточки**: название, пара полей,
  описание. Добавлять и править их можно и в режиме "игра" - предмет
  нашли посреди сессии, искать кнопку "Редактировать" не нужно. Описание
  пишется в редакторе TipTap 2.x (жирный, курсив, списки, подзаголовок) -
  тот же, что в LSS, поэтому импортированные тексты правятся без потерь.
  Редактор грузится отдельным куском кода только при правке.
- **Поиск по листу** - по всем вкладкам сразу: карточки (название, поля,
  текст описания), строки таблиц, навыки, поля.
- **Расчётов нет**, кроме модификатора характеристики: `floor((x-10)/2)` -
  арифметика, а не правило. Бонусы навыков, атаки, КД игрок пишет сам.
- **Пределы чисел** (`min`/`max` в схеме: характеристика 1-30, уровень 1-20,
  бонус навыка −10…+30) - защита от опечатки (`+99` вместо `+9`), а не
  правило: с запасом под хоумбрю, правятся в файле схемы. Вне пределов и
  дробное форма не сохраняет. Сервер их не проверяет - это не защита от
  злоумышленника; от раздувания данных сервер защищает форма данных.
- **Сервер правил не знает.** `data` - JSON, `sheet_data.py` проверяет
  только форму: путь к полю из простых сегментов, значения - обычный
  JSON, размер и глубина ограничены. Схему на сервере не дублируем.
- **Правка по полям** (`set: {"путь.к.полю": значение}`), а не листом
  целиком: ГМ и игрок, правящие разные поля, не затирают друг друга.
  Таблицы (оружие, заклинания) записываются целиком.
- **Видимость**: лист и все изменения уходят только владельцу и ГМ.
  Другим игрокам - ни при загрузке, ни в живых обновлениях. Чужой лист для
  игрока - "нет такого персонажа", а не "нельзя".

### Импорт из Long Story Short

Лист можно заполнить руками или импортировать JSON в формате Long Story
Short (`jsonType: "character"`, `version: "2"`) - его отдаёт кнопка
"скачать" на mycharacterbuilder.com и сам LSS.

- **Импорт формата, а не интеграция с сайтом.** У mycharacterbuilder.com
  и LSS нет открытого API для такого, а ходить на чужой сайт за игрока
  (логины, скрейпинг) - хрупко и сомнительно. Файл игрок скачивает сам и
  сам решает, что отдать. Формат - единственная точка связи: сайт может
  поменяться, файл на руках у игрока останется.
- **Своя схема, а не LSS как есть.** Адаптер `server/app/importers/lss.py`
  переводит файл в схему листа Lanterna. Формат LSS версионирован и
  поменяется; если сделать его внутренним, его версия стала бы версией
  нашего листа, а ручная форма и другие источники подстраивались бы под
  чужие решения. Исходный файл хранится рядом с листом целиком
  (`source_json`): поменялся адаптер - "Переимпортировать" прогонит файл
  заново. Ручные правки при этом пропадают, интерфейс предупреждает.
- **Тексты едут с персонажем, правил в ядре нет.** Разделы текстов из
  файла становятся карточками умений (снаряжение - карточкой предмета) с
  описанием-документом TipTap; id карточки - из ключа LSS, так что
  переимпорт даёт те же карточки, а не дубли. Сервер их не понимает и не исполняет: "Второе дыхание
  восстанавливает 1к10 + уровень" - это текст для игрока, а не код.
  Адаптер переносит значения из поля в поле и ничего не считает (бонусы
  навыков, например, не выводит).
- **Проверки:** файл не больше 512 КБ; `jsonType`/`version` сверяются, и
  неизвестная версия - понятная ошибка, а не падение; поле `data` - JSON
  строкой внутри JSON, разбирается вторым `json.loads`; числа вне пределов
  схемы обрезаются до границы. Тест на образце - `tests/test_lss.py`.
- **Тексты - XSS-граница.** Файл присылает игрок, а текст увидит вся
  кампания. Поэтому два слоя. Сервер (`richtext.py`) пропускает каждый
  документ TipTap - и из импорта, и из редактора (любой `{"type": "doc"}`
  в `character.update`) - через белый список: абзацы, списки, заголовок,
  перенос, текст с bold/italic, ссылки на ресурсы листа; остальное
  выбрасывает. Клиент (`RichText.tsx`) рисует узлы React-элементами по
  такому же списку; редактор включает только эти узлы, а документ перед
  загрузкой в него проходит тот же список (`richDoc.ts`). `innerHTML` и
  `dangerouslySetInnerHTML` в проекте запрещены.

### Ссылки и dnd.su

У заклинаний и предметов есть поле "ссылка": игрок сам вставляет ссылку,
например на dnd.su. Принимаются только `https`, открываются в новой
вкладке с `rel="noopener noreferrer"`. Проверка стоит там, где ссылка
**рисуется**: лист приходит и из формы, и из файла игрока, и `javascript:`
в href выполнился бы у всех, кто откроет лист.

Контент dnd.su - переводы книг Wizards of the Coast. Копировать его в
проект нельзя, только ссылаться. Публичного поиска у dnd.su нет: адреса
не угадываем и сайт не скрейпим - ссылку вставляет игрок.

## Роли

Две роли: ГМ и игрок - флаг `is_gm` у аккаунта. Модель как в Foundry:
**публичной регистрации нет**. Открытая регистрация на сервере для своей
группы не нужна и только добавляет мусорные аккаунты.

### Приглашения

Аккаунт появляется только по одноразовой ссылке от мастера
(`?invite=<код>`), но **имя и пароль игрок придумывает сам**. Мастер не
должен знать пароли игроков: тот же пароль у человека может стоять и
где-то ещё. Поэтому и "забыл пароль" - тоже ссылка, а не пароль,
который мастер вбивает за игрока.

- Код - 32 случайных байта, в базе только sha256. Сам код уходит один раз,
  в `reply` мастеру, который его создал; в списке у ГМ - только срок.
- Ссылка одноразовая и живёт 7 дней. Принятая, отозванная и просроченная
  отвечают одинаково: "не найдено или истекло".
- Сброс пароля по ссылке закрывает все прежние сессии игрока и его
  открытые сокеты: если пароль меняют из-за чужого входа, чужой вылетает.
- Ссылку открыли - её экран важнее текущей сессии в браузере: её
  открывают, чтобы завести аккаунт, а не продолжить чужой вход.
- Эндпоинты `/api/invite/info` и `/api/invite/accept` - REST, а не команды
  сокета: у приглашённого ещё нет сессии, а сокет пускает только с ней.

### Вход и сессии

- Пароли - только argon2id (`argon2-cffi`). Открытыми не хранятся и не
  логируются. Хеширование - в отдельном потоке: argon2 намеренно медленный,
  и вход одного игрока не должен замораживать сокеты остальных.
- На "нет такого имени" и "неверный пароль" - один ответ, и пароль
  проверяется даже для несуществующего имени (против фиктивного хеша):
  иначе по ответу или по времени было бы видно, какие имена есть.
- Сессия - случайный токен в **httpOnly** cookie (скрипт страницы его не
  прочтёт), `SameSite=Lax` (чужой сайт не отправит от имени игрока ни POST,
  ни websocket). В базе - только sha256 токена: утёкшая база не даёт
  войти чужими сессиями.
- Срок сессии (30 дней) проверяет и сервер, а не только браузер по
  `max_age` cookie: украденный токен можно слать и после срока. Просроченная
  сессия удаляется при первой же попытке входа с ней.
- Выход закрывает сокеты **этой** сессии (другие вкладки того же браузера
  уходят на экран входа), но не другие входы игрока - телефон, второй
  компьютер. Для этого в `Actor` лежит хеш сессии.
- `Actor` (id, имя, `is_gm`) берётся только из сессии. Имени в адресе
  сокета больше нет: его мог подставить любой.
- Websocket проверяет заголовок `Origin`: браузер шлёт cookie на сокет с
  любой страницы, и чужой сайт мог бы открыть его от имени игрока.
  Пускаем адреса из `FRONTEND_URL` (можно несколько через запятую) и
  страницу с того же адреса, куда идёт сокет (`Origin` == `Host`) - иначе
  отвалились бы `127.0.0.1` и адрес в локальной сети, по которому заходят
  игроки. Без `Origin` - не браузер (скрипты, smoke_test); чужой сайт в
  браузере `Origin` шлёт всегда.
- `<meta name="referrer" content="no-referrer">`: ссылки ГМ и приглашения
  несут секрет в адресе, и он не должен уходить в `Referer` на внешние сайты.
- Удалённого игрока сервер выгоняет сразу: шлёт `campaign` без него и
  закрывает его сокеты. Его токены и стены переходят мастеру, а не
  становятся общими - общий токен может двигать кто угодно.

Не сделано: ограничение попыток входа, HTTPS (cookie без `Secure`, потому
что локально всё по http), смена пароля самим игроком.

### Ключ ГМ

Ключ - способ **первого входа мастера**: по ссылке с ключом он создаёт
свой аккаунт (имя и пароль), дальше входит как все. Если пароль забыт,
ссылка с ключом снова пускает мастером: кто знает ключ, тот и так
владеет сервером.

- Ключ задаётся `LANTERNA_GM_KEY` или создаётся при первом запуске в
  `server/gm_key.txt` (не в git). Файл, а не новый ключ на каждый старт:
  `uvicorn --reload` перезапускается на каждую правку, ГМ терял бы права.
- Ссылку `...?gm=<ключ>` сервер печатает **только в момент создания
  ключа**, на остальных стартах - путь к файлу. Лог печатается на каждый
  перезапуск (с `--reload` это каждая правка), а логи вставляют в чаты.
  Ссылку по запросу даёт `./dev.sh gm`.
- Клиент забирает ключ из адресной строки при загрузке и сразу убирает
  его оттуда, обменивает на сессию и больше не хранит.

Хендлеры проверяют права по `Actor` сами. Клиент знает свою роль только
чтобы показать или спрятать инструменты.

Что сейчас только у ГМ: `scene.update` (карта, клетка, размер сцены),
загрузка файлов, стены, сцены, игроки, чужие токены.

### Права

Одно правило на всё: **своё правит владелец, чужое - только ГМ**.
Проверяет `_require_owner` в handlers.py, ГМ она пропускает. Мастер
ведёт партию и убирает за всеми, а игрок не должен портить чужое -
даже случайно. Двигать тоже: своего персонажа ходит игрок, монстров
и чужих - мастер.

Кроме владения:

- **Стены ставит только ГМ.** Это разметка карты. Игрок со стенами мог
  бы запереть других или отгородиться от монстров. Инструменты «Стена» и
  «Стереть» игроку не показываются.
- **Владельца токена меняет только ГМ.** Иначе игрок сделал бы свой
  токен общим (`owner = null`) или "подарил" его, и правила выше
  перестали бы что-то значить.
- **Картинки - только загруженные файлы.** `image_url` токена и фон сцены
  проверяет одна функция `_upload_url`: адрес вида `/uploads/<hex>.<ext>`
  и файл реально существует. Произвольный URL заставил бы браузеры всех
  игроков ходить на чужой сервер.

Это не противоречит правилу «отменять можно только своё»: Ctrl+Z
по-прежнему убирает только стены этого клиента. Удаление чужого - явное
действие ГМ (режим «Стереть», Delete на выбранном), а не горячая
клавиша отмены.

## Что осознанно отложено

- Динамическое освещение и полигоны видимости - после того, как по карте можно будет просто играть.
- Туман войны с сохранением.
- Автоматика правил в листе персонажа (пересчёт бонусов, выбор класса). Лист - форма, см. "Лист персонажа".
- Голос, LiveKit.
- Ограничение попыток входа и HTTPS. Аккаунты и сессии есть, но перебор паролей ничем, кроме медленного argon2, не тормозится, а cookie без `Secure`.
- Несколько кампаний у одного мастера. Модель готова (всё привязано к
  Campaign), не хватает выбора кампании и кампании в адресе. Открытый
  вопрос: аккаунт на кампанию (как сейчас) или на сервер с ролью в
  каждой кампании. Решить до появления реальных пользователей.
- Генератор событий в духе RimWorld Director. Делается поздно, но почти не зависит от канваса, так что может идти параллельно.
- Порядок до освещения: редактор стен/дверей/окон -> видимость
  токена -> источники света -> туман войны. Свет считается от стен,
  без них его не на чем проверять.
- Импорт Universal VTT (.uvtt, .dd2vtt, .df2vtt - один формат):
  картинка, клетка, стены, порталы, свет. Ложится на нашу модель:
  дверь/окно = kind, барьер = стена с blocks_sight=false. Нужна
  сущность Light (позиция, радиус, цвет, яркость). Может идти раньше
  собственного редактора - даёт размеченные стены для отладки света.
- Фигуры (Drawing: тип, точки, заливка, слой), галочка "фигура
  создаёт стены". Кисть - векторные мазки с упрощением, не растр.
- Ассеты: главное - библиотека с загрузкой паков мастера. Стартовый
  набор - процедурное (кровь, трава, земля), CC0 (Kenney), сгенери-
  рованное только с пометкой. Чужие паки в репозиторий не класть:
  большинство лицензий запрещает распространение.
- Перевод: строки интерфейса в ru.json/en.json, сервер шлёт коды
  ошибок (wall_blocked, gm_only), а не текст. Кубы понимают d и к.
- Лист персонажа: форма + импорт LSS (своя схема, LSS - через
  адаптер). dnd.su - только ссылки, которые вставляет игрок: контент
  там - переводы книг WotC, парсить и копировать нельзя.
  Создатель персонажа с проверкой правил - не делаем.
- Запуск одной командой, фронт и API на одном порту, туннель
  (Cloudflare Tunnel) вместо проброса портов.
- Токены слоя gm сейчас уходят всем игрокам в снапшоте - утечка,
  как была со скрытыми сценами. Закрыть до того, как появится UI
  для этого слоя.
## Стек

- Бэкенд: Python 3.12, FastAPI, SQLAlchemy 2 async, Postgres (SQLite как fallback для локального запуска без docker)
- Фронтенд: React 18, TypeScript, Vite, PixiJS 8 для сцены, zustand для состояния
- Инфра: docker compose

React отвечает только за UI вокруг канваса. Внутрь сцены React не лезет - там императивный PixiJS. Смешивать эти две модели - верный способ получить тормоза и невоспроизводимые баги.
